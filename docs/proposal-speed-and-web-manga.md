# 速度分析與「網頁漫畫整頁翻譯」提案

2026-10-03。第一部分是實際量測找出的瓶頸和優化方案；第二部分是網頁漫畫整頁翻譯的研究和建議。
數字都是在這台電腦（RTX 4070、Windows 11、螢幕縮放 150%）上用 `tmw_perf_report`、`tmw_overlay_preview`
和 Python 的 ONNX Runtime 1.24.4（和主程式同一版）量的。

---

## 第一部分：慢在哪裡

### 1. 使用者感受到的等待，由哪幾段組成

以「透鏡放在一頁日文漫畫上、漫畫模式、本機 hy-mt2 翻譯」為例（暖機之後）：

| 階段 | 耗時 | 說明 |
|---|---|---|
| 等畫面穩定 | 300 ms＋最多 100 ms | 漫畫情境 300 ms、網頁 400 ms、遊戲 600 ms；每 100 ms 才取樣一次 |
| 擷取 | 幾 ms | |
| 文字偵測 | 18 ms | 已經固定輸入大小，很快 |
| **文字辨識** | **76～168 ms（偶爾 850 ms）** | 見第 2 點，**可以大幅改善** |
| 對話框偵測 | 37 ms | 漫畫模式才有 |
| **manga-ocr 重讀直排對白** | **236～459 ms** | 見第 3 點，**OCR 裡最大的一塊** |
| **翻譯** | **本機 hy-mt2 1.0～2.2 秒**（第一次 11 秒，載入模型） | 網路或 LLM 決定，見第 4 點 |
| 背景修補（LaMa） | 每塊約 130 ms | 只有背景不是純色的段落 |
| 合計 | **約 2～3.5 秒** | 用 Google 翻譯約 1～1.5 秒 |

一般模式（非漫畫）的 OCR，依透鏡大小和行數：

| 內容 | 透鏡 720×405 | 透鏡 1000×1400 |
|---|---|---|
| 日文漫畫 | 69 ms | 153 ms |
| 英文漫畫 | 88 ms | 173 ms |
| 韓文條漫 | 50 ms | 58 ms |
| 日文遊戲 | 18～58 ms | 76 ms |
| 英文網頁 | **163 ms** | **174 ms** |

**結論：慢的地方依序是「翻譯」＞「manga-ocr 重讀」＞「等畫面穩定」＞「文字辨識」。**
前處理、解碼、資料複製都只有幾毫秒，不是問題。

### 2. 文字辨識：DirectML 的「新形狀」問題（找到根本原因）

拆開來量：一張網頁截圖只有 5 行字，因為寬度不同被分成 3 批，**每批光推論就要 28～50 ms，只有 1 行的那批也要 28 ms**。
同一個模型、同樣的輸入，用 Python 單獨量：

- 新建的工作階段、**第一次就用這個形狀**：1 行×寬 384 只要 **3.6 ms**
- 同一個工作階段先跑過別的形狀，**之後這個形狀永遠要 29 ms**（慢 8 倍）
- 只固定批次、或只固定寬度：一樣只有第一個形狀快
- 關掉 metacommands：變動的形狀變成 14 ms，但原本快的形狀變慢，仍遠不如 3.6 ms
- 「動態圖形融合」選項：沒有效果

也就是說，**DirectML 只有在形狀固定時才把整個模型編譯成一張最佳化的圖**。專案在 M1-03 對偵測模型遇過同一件事，
所以偵測已經固定輸入大小；但辨識的批次和寬度每次都不同，幾乎每一批都走慢的那條路。
第一次遇到新形狀時還要額外準備，所以偶爾會出現 850 ms 的尖峰。

固定形狀之後的速度（medium 模型）：1 行×384 = 3.2 ms、8 行×640 = 26 ms、4 行×1280 = 24 ms、16 行×640 = 50 ms。
代價是**每個固定形狀要一個工作階段，每個多佔 150～220 MB 記憶體**。

**建議做法**：準備 2～3 個固定形狀（例如「16 行×寬 320」給短的直排、「8 行×寬 640」、「4 行×寬 1280」給長的橫排），
每一批補滿到最接近的形狀；放不進的才走現在的動態路線。
預估：網頁 5 行從 116 ms 降到約 30～50 ms；整頁漫畫從 150～260 ms 降到約 60～100 ms，而且沒有 850 ms 的尖峰。
記憶體多約 300～400 MB，要再量實際值決定開幾個。
另外 small 模型在固定形狀下又快一倍（8 行×640 = 14 ms），但準確度較低（M0-11 選 medium 的原因），只建議給網頁模式的批次處理評估。

### 3. manga-ocr：逐字解碼，每一步都是新形狀

manga-ocr 每解一個字就跑一次解碼器，前面累積的 K/V 每一步都變長 → 每一步都是新形狀。
實測每一步約 1.7 ms（DirectML）或 2.4 ms（CPU），一頁 6～10 個直排對話框、每個 15～30 字，加起來就是 240～460 ms。
編碼器在 DirectML 上只要 4.5 ms，不是問題。

**建議做法**（擇一或都做）：

1. **一頁的對話框一起解碼（批次）**：步數從「所有字數的總和」降到「最長那個對話框的字數」，預估快 3～5 倍
   （約 240～460 ms → 60～120 ms）。要用 `tools/eval/export_manga_decoder.py` 重新匯出成可變批次的模型。
2. **固定長度的 K/V（加遮罩）**：每一步形狀都一樣，走快的路線；可以和 1 一起做。
3. 只重讀 PP-OCR 沒把握的對話框：省最多，但要重新評估 CER（M2-03 的 10.4% → 5.0% 是全部重讀量出來的）。

**已完成（1＋2 一起做）**：

- 重新匯出：解碼器可變批次（`batch`）、K/V 固定 96 格（`slots`）加遮罩。一頁的直排對白一次交給 manga-ocr，
  依字數上限排序、每 8 個一批同步逐字解碼；DirectML 上批次固定 8（不足補空白），CPU 有幾個送幾個。
- K/V 用 ONNX Runtime 的 IoBinding 留在顯示卡上，每一步只送字、收 logits。不這樣做的話一批 8 個每一步要來回搬約 19 MB，
  比計算還慢（Python 量測：每步 6.2 對 3.2 ms）。
- 實作後量出新的瓶頸是**編碼器**：關掉圖形最佳化時每張 13 ms（當初為了省記憶體關掉，那時候時間都在解碼，看不出差別）。
  打開後 5.3 ms，代價是漫畫模式的峰值工作集多約 270 MB（1203 → 1479 MB）。試過先存好最佳化的模型再關掉最佳化載入：
  記憶體一樣多（1460 MB），extended 等級的檔案還只能在 DirectML 上跑，所以直接在載入時最佳化。
- 結果（私人漫畫集 10 頁、124 個直排對白，DirectML）：**文字 124 段和舊版完全相同**；manga-ocr 總時間 2717 → 1235～1439 ms，
  每頁 150～430 ms → 80～200 ms。剩下的時間約一半是編碼器（每個對話框 5 ms），一半是逐字解碼（每批 15～40 ms）。
- K/V 只有 96 格：最多讀 95 個字。量測的直排對白最長 38 字；唯一超過的是一直重複同一個字停不下來的細長註解，
  那種區塊本來就不交給 manga-ocr（高超過寬的 10 倍）。

### 4. 翻譯：最大的一塊，但多半不在我們手上

- Google 免費端點：約 0.3～0.6 秒，但今天測試次數多就被限流（HTTP 429）。
- 本機 hy-mt2（Ollama）：一頁 1～2 秒；**閒置後第一次要 11 秒**（Ollama 預設 5 分鐘沒用就卸載模型）。
- Claude 批次：4.6 秒（M2-07 實測）。

**建議做法**：

1. **先顯示、後補譯文**：OCR 完先把結果視窗的原文和覆蓋層的位置準備好，譯文一段一段補上（LLM 用串流，翻完一段就畫一段）。
   總時間不變，但第一個譯文出現的時間可以從 2 秒降到幾百毫秒。
2. **讓 Ollama 的模型常駐**：請求帶 `keep_alive`（例如 30 分鐘），避免閒置後的 11 秒。很小的改動。
3. 已經有逐段快取（畫面只變一個對話框時其他不重翻），維持。

### 5. 等畫面穩定：可以「先做、變了再取消」

現在要等 300～600 ms 確定畫面不動才開始處理。可以在畫面停下 100 ms 時就**先開始 OCR**，
如果在設定的穩定時間內又變了，就取消（工作佇列本來就支援取消）。OCR 在本機、取消沒有代價；
**翻譯要等真的穩定了才送**，避免付費引擎多花錢。預估省 200～500 ms。

**已完成**：

- `AutoTrigger`：等待穩定中，畫面停下 100 ms（`prepareAfter`）就發出一次 `onPrepare`，帶一個票號。之後畫面一變、
  透鏡一動，票號就作廢，停下來再預先做一次；和上一次處理過的內容一樣時不做（到時候也不會處理）。
  等待時間本來就不比 100 ms 長時不做。
- 預先工作只做 OCR（包括漫畫模式的 manga-ocr 重讀），結果依票號記在 `Pipeline` 的透鏡記憶裡；不記原文、不翻譯、
  沒有結果送回 UI。正式處理時票號相同、辨識語言設定和畫面大小沒變就直接沿用，用過即丟。
- 工作執行緒：正式處理送來時，同一個透鏡進行中的預先工作不取消（同一個畫面），讓它做完，正式處理排在後面直接沿用。
  新的預先工作送來時照舊取消舊的。
- 結果：預設 400 ms 的等待裡，OCR 在後 300 ms 內做完，等待結束後只剩翻譯和畫覆蓋層。漫畫模式（OCR＋重讀約 250～400 ms）
  幾乎整段省下；網頁、遊戲（約 50～100 ms）也全部省下。整合測試的記錄裡看得到「OCR 在等畫面穩定時就做好了」。
- 代價：畫面每停下 100～400 ms 又變（例如捲動到一半停一下）就多做一次 OCR。都在本機、可以取消，不花錢。

### 6. 建議的優化順序

| 順序 | 項目 | 預估省下 | 工作量 |
|---|---|---|---|
| 1 | Ollama `keep_alive` | 閒置後第一次的 10 秒 | 很小 |
| 2 | 辨識改用固定形狀的工作階段 | 60～160 ms，消除 850 ms 尖峰 | 中 |
| 3 | manga-ocr 批次解碼（重新匯出） | 180～350 ms（漫畫模式） | 中 |
| 4 | 先做 OCR、變了再取消 | 200～500 ms | 中 |
| 5 | 譯文一段一段顯示（串流） | 第一段譯文提早約 1 秒以上 | 中大 |

1～4 做完，漫畫模式＋本機 LLM 預估從 2～3.5 秒降到約 1.3～2.5 秒，其中大部分剩下翻譯本身。
這些優化對第二部分的網頁模式一樣有用（尤其 2 和 3，網頁模式一次處理整章，吞吐量就是靠它們）。

## 第二部分：網頁漫畫整頁翻譯

### 1. 目標

像以前 Google 翻譯整頁那樣，打開漫畫網頁就把**整章所有圖片裡的文字**翻好、蓋上去；
使用者往下捲時譯文已經在那裡，**不必停下來等**。只針對在網頁上看漫畫。

### 2. 該 fork 新工具，還是當成新功能？

**建議：同一個倉庫、同一套安裝程式，新增「網頁模式」——一個瀏覽器擴充功能，加上和主程式共用引擎的本機服務。不要 fork。**

理由：

- 真正困難、花了最多時間的部分——OCR（PP-OCR、comic-text-detector、manga-ocr）、ルビ判斷、翻譯引擎鏈和快取、
  專有名詞表、覆蓋層的版面（直排、字級、顏色、描邊、ルビ）、LaMa 修補——**網頁模式要的完全一樣**。
  fork 之後兩邊各自修 bug、各自調門檻，很快就會分岔。
- 兩邊都要載入模型（約 1～1.6 GB 記憶體）。同一個程式裡只載一份，同時開透鏡和看網頁漫畫才不會吃掉兩倍記憶體和顯示卡。
- 設定（引擎、金鑰、字型、名詞表）共用，使用者只設定一次。

不同的只有「圖片從哪裡來」（網頁的 `<img>` 而不是螢幕截圖）和「譯文畫在哪裡」（網頁上而不是螢幕上的覆蓋視窗），
這兩件事由擴充功能負責。

**不建議的做法**：

- **純擴充功能（用 WebGPU／ONNX Runtime Web 在瀏覽器裡跑模型）**：模型要再下載一次（數百 MB），速度和記憶體都比原生差，
  manga-ocr 的逐字解碼在瀏覽器裡更慢，等於重寫一套引擎。
- **主程式自動捲動網頁、截圖翻譯**：脆弱（每個網站捲法不同）、看不到還沒載入的圖、會干擾使用者操作。

### 3. 架構

```
┌──────────── 瀏覽器（Chrome／Edge，之後 Firefox）────────────┐
│ 內容腳本（每個分頁）                                          │
│  - 找出漫畫圖片（<img>、srcset、懶載入、動態加入的）          │
│  - 監看捲動位置，決定處理順序                                │
│  - 把譯文疊在每張圖片上（跟著縮放、版面變動一起動）          │
│        │                                                      │
│ 背景 service worker                                           │
│  - 用擴充功能的權限抓圖片的原始位元組（不受網頁 CORS 限制）  │
│  - 在瀏覽器裡解碼（WebP／AVIF 都能解）、算圖片的雜湊          │
│  - 和本機服務溝通（原生訊息）                                │
└──────────────┬──────────────────────────────────────────────┘
               │ 原生訊息（Native Messaging，只接受我們的擴充功能）
┌──────────────▼──────────────┐      具名管道（只有本人帳號能連）
│ tmw_web_host.exe（很薄的轉送）│ ───────────────────────────────┐
└──────────────────────────────┘                                  │
┌─────────────────────────────────────────────────────────────────▼─┐
│ Translation Magic Window 主程式（已經在跑的那個，沒在跑就背景啟動）│
│  - 工作佇列：透鏡的工作優先，網頁的工作在空檔做                   │
│  - 整章批次：偵測 → 所有圖片的行一起辨識 → 對話框一起 manga-ocr  │
│    → 整章一起翻譯（同一個 LLM 請求帶完整上下文）→ 規劃覆蓋層      │
│  - 依圖片雜湊存進磁碟快取：同一章再看一次是瞬間                   │
└───────────────────────────────────────────────────────────────────┘
```

**為什麼用原生訊息（Native Messaging）而不是本機 HTTP 服務**：

- 本機開一個 HTTP 埠，任何網頁都可能試著連，要自己做驗證；Chrome 142 起網頁連 `localhost` 還會跳權限提示。
- 原生訊息由瀏覽器控管，只有清單裡列出的擴充功能能連，不必開埠。
- 限制：**主程式傳給擴充功能的每則訊息最多 1 MB**（反方向 64 MiB，送原圖沒問題）。所以**不要傳回整張翻好的圖**，
  只傳「覆蓋資料」：每段的位置、譯文、顏色、方向、ルビ，加上背景修補的小圖（每塊幾十 KB，太大就分段）。

**譯文怎麼畫在網頁上**：建議在每張圖片上方疊一層（同樣大小、跟著 CSS 縮放），用 HTML 畫譯文：

- 直排用 CSS `writing-mode: vertical-rl`，標點自動用直排字形，瀏覽器的排版比我們自己算還好。
- 字級用和現在一樣的「找放得進框的最大字級」（在 JS 裡二分搜尋），內建字型用 `@font-face` 載入。
- 背景修補的小圖用 `<img>` 放在對應位置。
- 不改原本的 `<img>`：有些閱讀器會檢查或重設圖片，疊一層比較不會壞掉。也可以一鍵切換原文／譯文。

另一個選擇是由主程式畫好整張覆蓋圖（沿用 DirectWrite 的繪製）再傳回去，好處是和桌面版一模一樣，
但要切成很多則 1 MB 以下的訊息。建議先用 HTML 版，必要時再比較。

### 4. 動態網頁的處理

| 情況 | 做法 |
|---|---|
| 圖片捲到附近才載入（lazy loading，`data-src`、`loading="lazy"`） | `MutationObserver` 監看 `src`／`srcset` 改變和新加入的 `<img>`；圖片載入完成才處理。可以選擇性地讀 `data-src` 先抓（各網站寫法不同，先做通用的，常見網站再加規則） |
| 無限捲動、一章一章接下去 | 同上，新的圖片加入就排進佇列；依「離畫面多近」決定順序 |
| 單頁應用換章（網址變了但頁面沒重新載入） | 監看 `history.pushState`／`popstate`，換章時清空佇列、取消舊章的工作 |
| 虛擬清單（捲過去的圖片被移出 DOM、回來時重建） | 疊層跟著圖片的**雜湊**走，不跟著 DOM 元素；重建時從快取立刻補回 |
| `<picture>`、`srcset`、不同解析度 | 用瀏覽器實際選中的 `currentSrc`；覆蓋資料用原圖的座標，按顯示大小縮放 |
| CSS 背景圖 | 第一版不處理（漫畫閱讀器很少用），之後視需要加 |
| 圖片在 `<iframe>` 裡 | 內容腳本設 `all_frames`；跨網域的 iframe 一樣可以注入（有權限的話） |
| 被切成很多段的條漫（一個對話框跨兩張圖） | 上下相接、寬度相同的圖片接起來一起偵測，再把結果分回兩張 |
| 很長的圖（800×12000） | 切成有重疊的區塊偵測，合併結果 |
| 用 canvas 畫、圖片被打散重組的閱讀器（官方平台常見） | **抓不到原圖**（抓到的是打散的碎片，canvas 讀不到像素）。不建議破解打散的規則（等於規避保護措施，法律上有疑慮）。改用：偵測到這種閱讀器時提示「這個網站請用透鏡」，桌面透鏡照常可用 |
| 防盜連（要 Referer 才給圖） | 背景 service worker 帶 cookie 抓；不行就用 `declarativeNetRequest` 補 Referer；再不行就退回上一列的提示 |

### 5. 效率

- **整章批次而不是一張一張**：偵測每張各跑一次，所有圖片的文字行集中起來用固定形狀一次辨識（第一部分第 2 點），
  對話框集中起來一次 manga-ocr（第一部分第 3 點）。GPU 的固定成本攤到整章。
- **整章一起翻譯**：LLM 一次拿到整章的對白，前後文、稱呼、口氣最一致，請求數也最少。
  先送畫面附近的幾頁，讓使用者馬上能看；其餘的在背景一次送。
- **依捲動位置排優先順序**：畫面上的 → 往下幾頁 → 其餘。使用者往下捲時，後面的通常已經好了。
- **磁碟快取**：依「圖片內容的雜湊＋引擎＋設定」存覆蓋資料，重看、上一頁、重新整理都是瞬間；也省付費引擎的錢。
- **和透鏡共用一個佇列**：透鏡的工作永遠優先（使用者正在等），網頁的工作在空檔做。
- 粗估（優化後）：一頁 OCR＋規劃約 0.3～0.5 秒（顯示卡），40 頁一章約 15～20 秒在背景完成；
  使用者看到第一頁譯文約需 1～2 秒（OCR＋翻譯第一批），之後幾乎不用等。

### 6. 想得到的問題

**技術**

1. **1 MB 訊息上限**：傳覆蓋資料、修補小圖分段，不傳整張圖（見上）。
2. **canvas／打散的閱讀器**：抓不到原圖，退回透鏡（見上）。這可能涵蓋不少官方平台，要先列出你常看的網站實際測。
3. **擴充功能的 service worker 會被瀏覽器停掉**（閒置約 30 秒）：長時間的工作放在主程式，擴充功能只負責收送；
   原生訊息的連線開著時 service worker 會保持運作，但仍要能斷線重連、從快取補回。
4. **廣告和介面圖片**：用大小、長寬比、位置（主要內容欄）過濾；使用者可以點圖片加入或排除，記在各網站的設定裡。
5. **版面變動**：視窗縮放、頁面縮放、圖片延遲載入撐開版面，用 `ResizeObserver` 讓疊層跟著圖片。
6. **記憶體**：一章 40 張大圖解碼後可能數百 MB。擴充功能只傳位元組、不留解碼後的圖；主程式處理完就釋放。
7. **兩邊版本對不上**：擴充功能和主程式的協定要有版本號，不相容時提示更新。
8. **Firefox**：原生訊息也支援，但清單格式和安裝的登錄位置不同，排在 Chrome／Edge 之後。

**發布和安裝**

9. 原生訊息要在登錄寫入主機的設定（`HKCU\Software\Google\Chrome\NativeMessagingHosts\...`，Edge 另一個位置），
   **安裝程式負責**，解除安裝時移除。
10. 擴充功能要上架 Chrome 線上應用程式商店（審核看權限：要「讀取所有網站」的權限，審核會比較嚴）；
    或只提供「開發人員模式載入」給自己用。**上架前要你決定**。
11. 沒有程式碼簽章時，Windows 對 `tmw_web_host.exe` 的態度和主程式一樣（SmartScreen），擴充功能本身不受影響。

**法律、隱私**

12. **著作權和網站條款**：個人閱讀時在自己電腦上翻譯、不轉存不散布，和現在的透鏡相同。但「整章自動處理」會一次讀取整章圖片，
    部分網站的條款禁止自動擷取；破解打散的圖片更有規避保護措施的問題（所以不做）。發布前要在說明裡寫清楚。
13. **隱私**：圖片不離開電腦，只有文字送到翻譯引擎（和現在一樣）。整章一起翻譯會一次送出整章的文字，付費引擎的費用要先顯示估計。
14. **付費引擎的費用**：一章 40 頁、每頁 10 段，比透鏡一頁一頁看多很多請求量；預設先用本機 LLM 或 Google，付費引擎要明確選擇。

**品質**

15. 擬聲詞、ルビ、側註的問題和透鏡一樣（M2-15、M2-16 仍待解）。
16. 網頁上的圖通常比螢幕截圖清楚（原始解析度），OCR 準確度應該會比透鏡好；壓縮很重的 JPEG 反而可能變差，要實測。

### 7. 建議的進行順序

1. **先做第一部分的優化 1～3**（keep_alive、固定形狀辨識、manga-ocr 批次）：網頁模式的吞吐量直接受益，透鏡也變快。
2. **列出你常看的漫畫網站**，我逐一檢查圖片是怎麼載入的（一般 `<img>`、懶載入、canvas 打散），決定第一版支援範圍。
3. **原型**：擴充功能（只做「找圖片、抓位元組、疊譯文」）＋主程式的網頁工作佇列，用一兩個網站跑通整章。
4. 動態網頁的各種情況、快取、優先順序。
5. 安裝程式加入原生訊息的登錄和擴充功能；決定是否上架。

### 9. 你回答之後的研究

**Magazine Pocket（講談社官方網站）**

- 單頁應用程式（Nuxt）。每一話的頁面清單由 API 回傳，請求要帶網站自己算的雜湊標頭，而且有 reCAPTCHA 分數檢查。
- 圖片在 CDN 上是**打亂過的拼圖**：API 給一個打亂用的種子，網站用 WebAssembly 把拼圖還原、畫到 `<canvas>` 上。
  頁面上看不到普通的 `<img>`，右鍵選單也被關掉。
- **做法：不去破解還原的演算法，也不自己呼叫 API**（等於繞過網站的保護，法律和維護上都不划算，網站一改就壞）。
  改讀「已經畫好的 canvas」：
  1. 擴充功能在頁面裡找到畫好的 canvas，試著讀像素。canvas 沒有被跨網域圖片「污染」的話就讀得到，這是最好的情況。
  2. 被污染、讀不到時，改用 `captureVisibleTab` 擷取畫面上看得到的部分（每秒最多 2 次），捲動到哪讀到哪。
  3. 都不行時，回到現在的透鏡（整頁譯文在這種網站上做不到，至少透鏡照樣能用）。
- 實作時要先實測第 1 步：canvas 是不是被污染，決定這個網站是「整章一次翻完」還是「捲到哪翻到哪」。

**raw 網站常見的載入方式**（不開你給的那個連結；以下是這類網站普遍的寫法，設計上都涵蓋）

- 普通的 `<img>`，但用延遲載入：真正的網址放在 `data-src`、`data-original`、`data-lazy-src` 之類的屬性，
  捲到附近才搬到 `src`。→ 屬性一起看；`MutationObserver` 盯著屬性變化。
- 一頁切成好幾條橫條（長條漫畫、或為了防盜切開）。→ 依位置把相鄰、同寬的圖片拼回一頁再 OCR，避免一句話被切成兩半。
- 圖片網址在別的網域、沒有開放跨網域。→ 擴充功能的背景頁有權限自己抓圖（不受頁面的跨網域限制）；抓不到再改用畫面擷取。
- 整個閱讀器在 `<iframe>` 裡。→ 內容腳本設定成在子框架裡也執行。
- `background-image` 當成圖片用。→ 也列入候選，用計算後的樣式取網址。

**廣告**

- 依「主要內容欄」判斷：先找頁面上最大的一串連續、同寬的圖片（漫畫本體），只翻那一欄；旁邊的、上下的不管。
- 再用規則排除：太小的（寬或高 < 200 像素）、長寬比明顯像橫幅的（> 4:1 且不在主要內容欄）、
  在 `<a>` 連到別的網域的、在第三方 `<iframe>` 裡的、網址屬於常見廣告網域的。
- 漫畫中間插的廣告圖：通常寬度和漫畫頁不同、或連結到外部網站，用前兩條大多能排除。排不掉的讓使用者點一下
  「這張不要翻」，依網站記住（網址樣式或位置），之後同一個網站自動排除。也可以反過來點「只翻這一欄」。
- 會遮住畫面的浮動廣告不處理（不是我們該擋的；使用者可以用自己的廣告阻擋擴充功能，兩者不衝突）。

**散布：不上架商店時的限制**

- Chrome 和 Edge 只讓三種方式裝擴充功能：商店、企業原則、開發人員模式的「載入未封裝項目」。
  Windows 上的 Chrome 不接受商店以外來源的 `.crx` 檔。
- 「載入未封裝項目」使用者可以自己做，但要打開開發人員模式；Edge 每次啟動會跳一個關不掉的提醒，
  Chrome 也會提醒（實作時再實測現在的版本）。安裝程式可以把擴充功能的資料夾放好、說明怎麼載入，但不能替使用者按。
- 用登錄檔的「企業原則」強制安裝可以不經商店，但這是給公司管電腦用的，而且仍然要指向商店上的項目或自架的更新網址、
  並且會讓瀏覽器顯示「由貴組織管理」，不建議。
- **可行的選擇**：
  1. 開發人員模式＋載入未封裝項目（不經審核、隨時更新；使用者要自己做幾個步驟，瀏覽器會一直提醒）
  2. 上架成「不公開」項目（不會出現在搜尋結果，只有拿到連結的人裝得到；要過審核，但安裝一鍵完成、自動更新）
- 建議 2：「不上架」如果是不想讓不相干的人找到，「不公開」就做得到；使用者體驗好很多。要不要這樣做**請你決定**，
  第一版原型先用 1 開發和測試，不影響。
