## 1. 概述

一個 Windows 桌面翻譯工具。使用者把一個可拖動、半透明的「透鏡」視窗放在任何畫面上（漫畫、遊戲、網頁），透鏡底下的文字會自動被辨識並翻譯成繁體中文。

- **第一階段**：翻譯結果以「原文／譯文對照」的形式顯示在獨立的結果視窗。
- **第二階段**：譯文直接覆蓋在原文位置上，並盡量還原原本的字型風格。

運作方式是「擷取螢幕 → OCR → 翻譯 → 顯示」，**不注入、也不修改其他程式**。

## 2. 需求與決策紀錄

### 2.1 已確認的需求

| 項目 | 決定 |
|---|---|
| 翻譯對象 | 漫畫、遊戲、網頁 |
| 直排文字 | 必須支援；自動判斷，也能手動切換 |
| 漫畫的小字和擬聲詞 | 振り仮名（ルビ）、作者刻意的特殊讀音、旁註、擬聲詞／擬態詞都要能辨識，並**一起翻譯出來**（不只當作翻譯的參考）：作者可能字面寫 A、角色唸出來或實際代表的是 B，用來營造反差、諷刺或內心的真實想法。字的大小差異也要還原（見 4.4、4.7、4.8） |
| 來源語言 | 日文、英文、韓文；可自動偵測，也可手動指定 |
| 目標語言 | 繁體中文（台灣用語）；程式內部保留目標語言參數，方便日後擴充 |
| 觸發條件 | 透鏡停止移動，且底下內容一段時間沒有變化 |
| 翻譯引擎 | 內建免費引擎（包含非官方端點），也支援付費 API 與雲端 LLM；使用者可自行更換 |
| 透鏡 | 中間點擊穿透；架構支援多個透鏡，**第一版只開放一個** |
| 結果視窗 | 原文與譯文成對顯示，可捲動瀏覽歷史；使用者自行擺放位置，不跟隨透鏡 |
| 歷史紀錄 | 只保存在記憶體中，關閉程式就清除；**不做匯出** |
| OCR 修正 | 暫時不做「手動修正 OCR 錯字後重新翻譯」 |
| 截圖／錄影 | 接受本工具的視窗不會出現在截圖、錄影和 OBS 中 |
| 開發語言 | C++ |
| 發布 | 開源（GPL-3.0） |
| 硬體支援 | 必須能在沒有獨立顯卡的電腦上執行（這類使用者改用雲端翻譯） |
| 作業系統 | 只支援 Windows 11 |

### 2.2 不做的事

- 注入其他程式、攔截程式內部的文字（Text Hooking）：有被反作弊系統判定違規的風險。
- 獨佔全螢幕的遊戲：覆蓋層無法顯示在上面，請使用者改用無邊框視窗模式。
- 手動修正 OCR 結果、匯出或長期保存歷史紀錄（目前不做）。
- 讓本工具的視窗出現在截圖或直播畫面中（「實況模式」留待日後再考慮）。

### 2.3 M0 技術驗證的結論

M0 用真實環境和 90 張真實截圖驗證每個高風險的技術點。選定的做法整理如下，數字和理由見各節。

| 項目 | 結論 | 詳見 |
|---|---|---|
| 透鏡視窗 | 分層視窗＋逐像素透明可行：點擊穿透跨程式有效、排除擷取有效、150% 縮放正常，拖動和縮放不閃爍，不需要自己處理滑鼠 | 4.1 |
| 擷取 | Windows.Graphics.Capture 擷取整個螢幕再於 GPU 裁切；關閉游標和黃色邊框；用 `MinUpdateInterval` 節流，回呼中不丟畫面 | 4.2 |
| 觸發 | 兩層變化偵測（64×64 縮圖）加狀態機；螢幕其他地方持續變化時，整台電腦的 CPU 約 0.17% | 4.3、5 |
| OCR 模型 | 一般和韓文的偵測都用 PP-OCRv6 medium，韓文辨識用 `korean_PP-OCRv5_mobile_rec`，沒有 GPU 時用 v6 small | 4.4「M0-11 的評測結果」 |
| 日文漫畫 | 直排用 manga-ocr 逐字解碼（對白 CER 1.9%），橫排和極細長的單行用 PP-OCR；對話框用 comic-text-detector 的文字區塊，擬聲詞的位置用它的文字遮罩 | 4.4 |
| 語言判斷 | 兩個辨識模型都跑，再依「韓文字母」和「假名或漢字」的行數，整個透鏡一起決定 | 4.4 |
| C++ 推論 | C++ 的 OCR 和 PaddleOCR 官方版文字完全相同、文字框誤差 0 像素；manga-ocr 的 ONNX 版和官方逐 token 相同（合成圖和真實裁切圖都驗證過） | 4.4 |
| 翻譯引擎 | 預設引擎鏈「LLM（使用者填金鑰）→ Google」，譯文一律經過 OpenCC 的 `s2twp`；本機 LLM 是離線選項 | 4.5「M0-12 的評測結果」 |
| 模型管理 | `tools/fetch_models/models.json` 固定版本並驗證 SHA-256；評測專用的模型另外放在 `tools/eval/models-eval.json` | 4.4、7 |

**還沒解決、要帶進後面里程碑的問題**

| 問題 | 處理 |
|---|---|
| OCR 速度超過預算（透鏡大小 283 ms，預算 150 ms） | M1-03：同一張畫面的多行合成一批，寬度補齊到固定級距 |
| 擬聲詞辨識不出來（所有模型的 CER 都在 80% 以上） | M2-16：對照表比對、專門的模型，或只標出位置 |
| 免費雲端 LLM 的每日額度很小 | 介面顯示額度用完並自動換下一個引擎；說明文件標示各引擎的免費額度 |
| DirectML.dll 的授權和 GPL-3.0 的相容性 | M5 發布前由你決定（見第 11 節） |

## 3. 系統架構

```
 ┌──────────────┐
 │ 透鏡視窗 ×N    │  Win32 分層視窗：邊框可拖動，中間點擊穿透，不會被擷取
 └──────┬───────┘
        ▼
 ┌──────────────┐      ┌──────────────────────┐
 │ 透鏡控制器 ×N  │◀────▶│ 擷取服務（WGC，共用）  │
 │ 狀態機 + 情境模式│      │ 螢幕擷取 → GPU 裁切     │
 └──────┬───────┘      └──────────────────────┘
        │ 變化偵測 → 內容穩定 → 送出工作（帶流水號）
        ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 處理佇列                                                       │
 │  OCR 服務：偵測 → 判斷橫直排 → 辨識 → 判斷語言 → 合併段落 → 閱讀順序  │
 │  翻譯服務：快取 → 引擎鏈（含備援）→ 對齊檢查 → OpenCC（s2twp）      │
 └──────┬──────────────────────────────────────────────────────┘
        ▼
 ┌──────────────┐     ┌──────────────────┐
 │ 歷史紀錄（記憶體）│────▶│ 結果視窗（Qt）      │  第一階段
 └──────┬───────┘     └──────────────────┘
        └────────────▶ 覆蓋層視窗 ×N（D2D/DirectWrite）   第二階段
```

### 3.1 共用與獨立的部分

- **每個透鏡各自擁有**：透鏡視窗、擷取範圍、狀態機、情境模式、流水號，以及第二階段的覆蓋層。
- **所有透鏡共用**：擷取服務、OCR 模型、翻譯服務（含快取和引擎鏈）、歷史紀錄、結果視窗。
- 結果視窗的每張卡片都會標示來源透鏡。

### 3.2 分層：core 與 platform

為了讓大部分邏輯都能寫單元測試，程式碼分成兩層：

| 層 | 內容 | 規則 |
|---|---|---|
| **core** | 狀態機、變化偵測演算法、合併段落、閱讀順序、語言判斷、翻譯對齊、引擎鏈、快取、歷史紀錄、設定遷移、座標換算 | **不依賴** Win32、D3D、Qt、網路。時間、畫面、翻譯引擎都透過介面（`IClock`、`IFrameSource`、`ITranslator`）注入，測試時換成假的實作 |
| **platform** | 透鏡視窗、WGC 擷取、系統匣、快捷鍵、DPAPI、Qt 視窗 | 盡量薄，只做「把系統 API 轉成 core 的介面」 |
| **ocr**、**net** | ONNX 推論；HTTP 和各家翻譯引擎 | 實作 core 的介面（`ITranslator`）。引擎只認得 `IHttpClient`，測試時換成回放錄好回應的假用戶端 |

### 3.3 執行緒模型

| 執行緒 | 職責 |
|---|---|
| UI 執行緒 | Qt 事件迴圈，同時處理 Win32 透鏡視窗的訊息 |
| 擷取執行緒 | WGC 的 frame pool 回呼、裁切、變化偵測 |
| 推論工作執行緒 | OCR 推論。模型推論依序執行，避免搶 GPU |
| 網路 I/O | 以非同步方式呼叫翻譯 API，支援 LLM 串流輸出 |

- **取消機制**：每次送出處理時，都會帶上該透鏡目前的流水號。**畫面變化或開始拖動時**，流水號都會加一。結果回來時，如果流水號和目前的不一樣，就直接丟棄。這可以避免舊位置的結果被套用到新位置。
- **跨執行緒更新 UI**：一律透過 Qt 的 queued signal 回到 UI 執行緒。

## 4. 模組設計

### 4.1 透鏡視窗

| 項目 | 做法 |
|---|---|
| 外觀 | `WS_EX_LAYERED` 搭配 `UpdateLayeredWindow`，逐像素設定透明度。邊框不透明，中間完全透明 |
| 點擊穿透 | 中間像素完全透明，系統會自動讓滑鼠事件穿透到底下的程式（跨程式也有效） |
| 抓取區 | 邊框外側加寬約 8～12px（依 DPI 縮放），透明度設為 1/255：肉眼幾乎看不到，但可以點擊，這樣細邊框也容易抓 |
| 拖動與縮放 | 左上方的把手用來拖動（`WM_NCHITTEST` 回傳 `HTCAPTION`），四邊和四角用來縮放（`HTLEFT`、`HTBOTTOMRIGHT` 等）。版面配置和點擊判定都放在 `core/lens_layout`，並有單元測試保證「看得到的像素」和「點得到的位置」完全一致 |
| 不搶焦點 | `WS_EX_NOACTIVATE`、`WS_EX_TOOLWINDOW`、`WS_EX_TOPMOST` |
| 排除擷取 | `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` |
| DPI | 程式宣告 Per-Monitor V2，所有座標一律使用實體像素；處理 `WM_DPICHANGED`，讓邊框粗細跟著縮放 |
| 狀態顯示 | 邊框顏色：橘＝拖動中、黃＝等待畫面穩定、紫＝處理中、藍＝顯示中（平常的狀態）。手動擷取時短暫閃綠色（成功）或紅色（失敗） |
| 系統匣圖示 | 透鏡不在工作列、也不會取得焦點，所以要透過系統匣選單開啟結果視窗、暫停或結束程式 |
| 單一執行個體 | 用具名 mutex 防止重複啟動。否則會出現兩組透鏡，快捷鍵也會註冊失敗 |

⚠️ **不要**用 `WM_NCHITTEST` 回傳 `HTTRANSPARENT` 來做穿透。它只對同一個執行緒的視窗有效，無法把滑鼠事件傳給其他程式。

⚠️ 分層視窗在系統的縮放迴圈中，每次尺寸改變都要重新呼叫 `UpdateLayeredWindow`，可能會閃爍或跟不上滑鼠。M0-05 實測（含 150% 縮放）沒有閃爍、也跟得上滑鼠，所以維持使用系統的拖動和縮放。

**本工具的所有視窗**（透鏡、覆蓋層、結果視窗、設定視窗）都要排除擷取。否則使用者把透鏡拖到結果視窗上時，程式會去翻譯自己的輸出。

### 4.2 擷取服務

- 使用 Windows.Graphics.Capture（C++/WinRT）擷取透鏡所在的整個螢幕，再用 `CopySubresourceRegion` 在 GPU 上裁切出透鏡範圍。
- `IsCursorCaptureEnabled = false`：擷取時不包含滑鼠游標。否則游標在透鏡範圍內移動，就會被當成內容變化。（`ScreenCapture::Options::captureCursor` 只給整合測試 IT-07 做正向對照用，正式程式一律關閉）
- `IsBorderRequired = false`：不顯示擷取時的黃色邊框。
- **節流**：高更新率螢幕每秒可能送出 144 張以上的畫面。用 `MinUpdateInterval` 讓系統把頻率限制在約每秒 10 張（Windows 11 24H2 起支援）。
- **回呼中不自行丟棄畫面**：如果在回呼裡丟掉畫面來節流，畫面之後靜止時系統就不會再送新畫面，程式會一直停在過時的內容。所以每張送來的畫面都在 GPU 內部複製一份（成本很低），比較昂貴的「讀回 CPU」只在需要時才做。系統不支援 `MinUpdateInterval` 時，改由使用端降低讀取頻率。
- **先在 GPU 上裁切再讀回**：只把需要的範圍複製到暫存材質再讀回 CPU。變化偵測（M0-07）只需要 64×64 的縮圖，只有真的要跑 OCR 時，才讀回完整的裁切畫面。
- **需要重建擷取的情況**：D3D 裝置遺失（例如驅動更新、GPU 重置）、顯示設定變更（解析度、螢幕插拔）、從睡眠恢復、透鏡移到另一個螢幕。
- 每個螢幕只開一個擷取工作階段，由該螢幕上的所有透鏡共用。
- 透鏡橫跨兩個螢幕時：第一版只擷取透鏡中心點所在的螢幕。
- HDR 螢幕以 BGRA8 格式擷取時顏色可能失真，已列入測試矩陣。

### 4.3 觸發狀態機與變化偵測

```
             WM_ENTERSIZEMOVE（流水號加一）
   ┌──────────────────────────────────────┐
   ▼                                      │
 拖動中 ──WM_EXITSIZEMOVE──▶ 等待穩定 ──穩定 settleMs──▶ 處理中 ──結果回來──▶ 顯示中
                              ▲  │ 畫面變化：重新計時       │                   │
                              │  └─────────────────────────┘                   │
                              ├──── 畫面變化：取消這次處理（流水號加一）──────────┤
                              └──────────────────── 畫面變化 ──────────────────┘
 快捷鍵手動觸發：除了「拖動中」以外的任何狀態，都直接進入「處理中」
```

**變化偵測**
1. 把裁切後的畫面縮成 64×64 的灰階縮圖，和上一張比較。
2. 平均絕對差超過門檻，或變化的像素比例超過門檻，就視為「有變化」。

**跳過重複處理**
- 內容穩定後，先把畫面和「上一次處理過的畫面」比較。一樣就不跑 OCR。
- OCR 結果和上一次一樣，就不翻譯，也不新增歷史卡片。

**遊戲模式的「只看文字區域」**

遊戲常有動態背景和閃爍的提示符號，整個畫面幾乎不會靜止。所以在第一次 OCR 之後改成兩層偵測：
- **文字框內**：用低門檻偵測，只要文字有變化就會觸發。
- **整個透鏡範圍**：用高門檻偵測，只有出現新對話框這類大變化才會觸發。

**初始參數**（M1 實測後再調整）

| 情境 | 取樣間隔 | settleMs | 偵測範圍 |
|---|---|---|---|
| 漫畫 | 100 ms | 300 ms | 整個透鏡範圍 |
| 網頁 | 100 ms | 400 ms | 整個透鏡範圍 |
| 遊戲 | 100 ms | 600 ms | 文字框內（低門檻）＋整個範圍（高門檻） |

### 4.4 OCR 流程

```
裁切後的畫面 → 文字偵測 → 判斷橫直排 → 文字辨識 → 判斷語言 → 合併段落 → 排出閱讀順序 → TextBlock[]
```

#### 模型配置

| 情境／語言 | 偵測 | 辨識 |
|---|---|---|
| 一般（日文、英文） | PP-OCRv6 medium | 同左（一個模型涵蓋日文和英文） |
| 韓文 | PP-OCRv6 medium | `korean_PP-OCRv5_mobile_rec`（PP-OCRv6 不支援韓文） |
| 漫畫（日文） | comic-text-detector：對話框用它的文字區塊，擬聲詞用它的文字遮罩 | 直排：manga-ocr 逐字解碼；橫排和極細長的單行：PP-OCRv6 medium |
| 沒有 GPU 的備案 | PP-OCRv6 small | 同左 |

以上是 M0-11 用 90 張真實截圖評測後選定的（見下方「M0-11 的評測結果」）。

**PP-OCRv6**（2026 年 6 月發布，設計初版時還沒有）：tiny／small／medium 三種大小，一個模型涵蓋中、英、日文和 46 種拉丁語系語言。官方數據中 medium 的偵測和辨識都比 PP-OCRv5 server 準確約 5 個百分點；tiny 不支援日文；**三種都不支援韓文**。它換了新的骨幹網路（PPLCNetV4），在 DirectML 上能不能跑、跑多快，在 M0-14 確認。PP-OCRv6、PP-OCRv5 和韓文模型的前後處理相同（偵測都用 DB 後處理，辨識都用 CTC 解碼），C++ 可以共用同一套程式，換版本只要換模型檔和字元表。

**模型來源**：PP-OCRv5、PP-OCRv6 和韓文模型都有 PaddlePaddle 官方在 Hugging Face 上提供的 ONNX 版本，不需要自己轉換。辨識模型的字元表放在同一個資料夾的 `inference.yml` 中。所有模型的下載網址（固定版本）、大小和 SHA-256 列在 `tools/fetch_models/models.json`。

所有模型都以 ONNX 格式透過 ONNX Runtime 執行。執行方式依序嘗試 DirectML，失敗則改用 CPU。

**執行環境**：ONNX Runtime 1.24.4（DirectML 版）加上 DirectML 1.15.4，從 NuGet 下載固定版本。DirectML 已進入持續維護，ONNX Runtime 的 DirectML 版停在 1.24.x，新功能移到 Windows ML。Windows ML 使用相同的 ONNX Runtime API，之後要改用它（例如 NVIDIA 顯卡改用 TensorRT RTX）時，只需要改建立工作階段的部分。

**DirectML 的限制**
- 必須關閉 memory pattern，並使用循序執行模式。
- 輸入尺寸一直變動時效率很差。所以偵測模型的輸入要對齊到少數幾種固定尺寸，辨識模型的寬度也要補齊到固定的級距。
- 補齊到固定級距後，右邊補的 0 會比官方版多，結果可能和官方版略有不同。M1 實作時要用同一套比對工具（見下方）量測差異。

#### C++ 實作和 PaddleOCR 的一致性

C++ 的前後處理（`src/ocr/`）逐步照著 PaddleOCR 官方實作（PaddleX 3.7）寫，同一張圖片的文字和文字框必須和官方版相同，用 `tools/eval/check_ocr_equivalence.py` 檢查（說明見 `tools/eval/README.md`）。幾個容易出錯的細節：

- **參數**用 PaddleOCR OCR 管線的預設值（`limit_side_len` 64、`limit_type` min、`thresh` 0.3、`box_thresh` 0.6、`unclip_ratio` 1.5），不是模型 `inference.yml` 裡的值。
- **numpy 的型別規則**：二值化門檻以 float32 比較；正規化是 float32 的先乘後加（不能合併成 FMA）；文字框座標換算用 float64；Python 的 `round` 是四捨六入五成雙。
- **文字框擴張**用和 pyclipper 相同的 Clipper 6.4.2（浮點座標往 0 的方向截斷成整數），不用 Clipper2。兩者擴張出來的頂點不同，文字框會差 1 個像素，連帶影響辨識結果。
- **辨識一次一張**：批次中的圖片會補齊成相同寬度，影響結果。
- **字元表**是 blank、`inference.yml` 的字元、空白字元，依序排列。

**M0-14 的結果**：6 個模型組合（PP-OCRv6 medium／small／tiny、PP-OCRv5 server／mobile、韓文）、9 張合成圖片（每組 32～45 行文字），C++ 在 CPU 和 DirectML 上辨識出的文字都和官方版完全相同，文字框誤差 0 像素。6 個辨識模型的完整字元表（合計約 9.3 萬個字元）也逐字相同。

**manga-ocr**

manga-ocr 是「編碼器（ViT）＋解碼器（BERT）」模型，要自己寫逐字產生的解碼迴圈和詞表對照。M0-15 的結果（`tools/eval/check_manga_ocr.py`，20 張合成對話框）：

- **ONNX 可行**：拆成 `encoder.onnx`（343 MB）和 `decoder.onnx`（117 MB），和 PyTorch 的數值差異在 2×10⁻⁵ 以內，DirectML 可以執行。
- **自己寫的解碼和官方完全一致**：官方的解碼是 beam search（4 個候選、不可重複的三字組、`length_penalty` 2.0、`early_stopping`），在 Python 逐步重現後，產生的 token 和官方完全相同（CPU 和 DirectML 都是）。M0-11 在 139 張真實漫畫的裁切圖上重跑，也完全相同。
- **官方的解碼會弄錯重複的字**：「不可重複的三字組」規則讓「ドドドドドド」變成「ドドドＦドド」、「ザアザアザア」變成「サアサアザア」、「ああああああ」變成「ぁぁぁあああ」。逐字解碼（每次取機率最高的字）這三張都正確，其餘 17 張和官方相同。擬聲詞常常是重複的字，所以**改用逐字解碼**（M0-11 用真實漫畫截圖確認，對白也比較準，見下方「M0-11 的評測結果」）。
- **速度**（還沒有 KV cache，每一步都重算整個序列）：編碼器 DirectML 23 ms、CPU 261 ms；逐字解碼 DirectML 353 ms、CPU 270 ms。解碼器只有 2 層，每一步的運算量很小，DirectML 每次呼叫的固定成本反而比運算大。C++ 版（M2-03）預計把解碼器匯出成有 KV cache 的版本並放在 CPU 上執行，編碼器放在 DirectML 上。
- **前處理**：轉灰階再轉回 RGB，用 PIL 的雙線性縮成 224×224；乘 1/255 時用 float64 計算再轉成 float32（transformers 的做法），C++ 要照做。
- **後處理**：移除空白、「…」換成「...」、連續的「・」「.」換成「.」，再把英數字轉成全形（例如 HP100 → ＨＰ１００），C++ 要照做。
- **執行環境**：官方套件搭配 transformers 5.x 時，權重要經過名稱轉換才能載入；參考環境用 transformers 4.57.6，檔案中的權重都照原本的名稱載入（`tools/eval/.venv-manga`）。

#### 漫畫的小字和擬聲詞

漫畫中除了對白之外，還有幾種文字都要辨識，並且**一起翻譯出來**（不只當作翻譯的參考）。作者常常字面寫 A、角色唸出來或實際代表的是 B，用來營造反差、諷刺或內心的真實想法，兩邊都要讓讀者看到：

| 種類 | 例子 | 處理方式 |
|---|---|---|
| 振り仮名：一般讀音 | 東京 旁邊的 とうきょう | 本文照常翻譯。ルビ只是發音，翻出來沒有意義，不另外翻譯 |
| 振り仮名：另有含義 | 本気 標 マジ、強敵 標 とも、未来 標 あした | 本文和ルビ**分別翻譯**，譯文保留上下對照：例如「認真」上面標「玩真的」 |
| 旁註、註釋 | 對話框外補充說明的小字 | 當成獨立的文字區塊翻譯，保留小字的樣式 |
| 擬聲詞／擬態詞 | ドキドキ、ガーン、ザアザア | 偵測對話框外的大型藝術字，用逐字解碼辨識（重複的字才會正確），翻譯時搭配擬聲詞對照表 |

- **資料結構**：`TextBlock` 加上 `kind`（對白、旁註、擬聲詞），以及每一行的位置和**字級**（直排是欄寬，橫排是行高）。ルビ記錄它標注的本文字元範圍、讀音，以及是「一般讀音」還是「另有含義」。
- **本文**：manga-ocr 會自動忽略ルビ，只輸出本文（M0-15 確認），所以本文不會混進讀音。
- **ルビ的偵測和辨識**：在同一個文字區塊內，找出字的大小不到旁邊本文的六成、而且位在本文右側（直排）或上方（橫排）的小字行，另外裁切辨識，再依位置對應到它標注的本文字元（直排看 y 座標的重疊，橫排看 x 座標）。
- **一般讀音還是另有含義**：用日文辭典（例如 JMdict、KANJIDIC2）查本文這個詞的讀音。ルビ（轉成平假名後）和辭典的讀音相同就是一般讀音；不同、辭典查不到，或是ルビ標在假名上，就當成另有含義。寧可多翻，也不要漏掉作者的用意。使用哪個辭典、授權是否相容，在 M2 確認。
- **翻譯方式**：見 4.5 的「振り仮名的翻譯」。
- **字級**：以「行」為單位記錄，不是整個區塊一個值。結果視窗和覆蓋層都依照它還原大小（見 4.7、4.8）。
- **擬聲詞的偵測**：M0-11 確認 comic-text-detector 的文字區塊幾乎不框擬聲詞，但它的文字遮罩蓋得到（日文 100%、英文 94%，誤標的背景很少），所以用遮罩找出對話框以外的文字位置。**辨識還沒有解法**：所有模型的 CER 都在 80% 以上，M2-16 要另外想辦法（對照表比對、專門的模型，或只標出位置）。
- **擬聲詞的翻譯**：內建常見擬聲詞的對照表（例如 ドキドキ → 怦怦、ザアザア → 嘩啦嘩啦，附上簡短說明）。查不到時交給翻譯引擎，並在提示中註明這是擬聲詞。

#### 漫畫的實測結果（M1-12 之後）

你用真的日文漫畫試用時回報「句子被切斷、中間夾著ルビ」。用 10 頁真實漫畫量測
（`tools/ocr_cli` 加上 `blocks` 欄位，會輸出 `core/text_layout` 合併後的段落）：

| 項目 | 數字 |
|---|---|
| OCR 行數 → 合併後段落 | 410 → 381（**幾乎沒合併**） |
| 只有一行的段落 | 98% |
| 3 個字以內的段落 | 44% |
| 整段都是假名（幾乎都是ルビ） | 36% |
| 正確答案的區塊數 | 142（對白 72、擬聲詞 46、其餘 24） |

逐對檢查「為什麼沒合併」（400 組相鄰配對）：

| 被擋下的原因 | 比例 |
|---|---|
| 字級差太多（ルビ 夾在主文之間、擬聲詞） | **63%** |
| 同欄但上下距離太遠（其實是不同對話框，擋對了） | 22% |
| 可合併 | 4% |

兩個根本問題：

1. **ルビ 被當成一般的文字行**。它就在主文那一欄旁邊，閱讀順序上夾在兩欄主文中間，
   字級又差 2 倍以上，於是「這兩欄是同一段」的判斷永遠斷在它身上。
2. **合併只看「閱讀順序上相鄰」的兩行**。被 ルビ 或擬聲詞插隊一次，後面整串就接不回來。

試過的改法（同樣 10 頁）：

**做完的結果**（同樣 10 頁，實際程式量測）：

| 版本 | 段落數 | ルビ |
|---|---|---|
| 改之前 | 401 | 0 |
| ＋ルビ附著（`core/ruby`）＋合併改成分群 | 289 | 106 |
| ＋短欄的方向用整頁多數決 | **232** | 106 |
| 正確答案 | 142 | 67 個帶ルビ的區塊 |

三個改動分別是：

1. **`core/ruby` 的 `attachRuby`**：把明顯是 ルビ 的行附到它標註的本文上，並依它在欄上的位置
   算出「標在第幾個字到第幾個字」。判斷依據都是量出來的——字級比中位數 0.46（上限取 0.75）、
   框和本文**重疊**（間距中位數 −0.17，所以不能用「在左邊還是右邊」判斷）、只蓋住本文的 31%。
2. **合併改成分群**：任意兩行相容就併成一群，不再只看閱讀順序上相鄰的那兩行。
3. **直排欄距上限 0.8 → 1.6 倍字級**，以及**短欄的方向用整頁多數決**：
   一兩個字的框接近正方形（佔 9%），從長寬比看不出方向，照著猜會把它孤立成自己一段。

還有距離的原因：擬聲詞本來就各自一段（正確答案裡有 46 個），以及部分對話框仍然沒併起來。
ルビ 偵測略為過頭（85 段帶 ルビ，正確答案 67），多出來的是小字的假名對白。

#### 直排的閱讀順序（試用後修正）

你回報「直排的句子有時候順序相反」。查出兩個 bug，第二個是主因：

1. **「是不是同一欄」用右緣的差距判斷**。欄寬不一致時（欄裡有窄字），兩個不同的欄會被
   誤判成同一欄，於是改用「上面的先」，順序就顛倒了。而且那種比較**不具備遞移性**，
   `std::sort` 要求嚴格弱序，本身就是未定義行為。現在改成先依水平重疊分欄，再依
   「第幾欄、欄內由上到下」排序（排的是索引排列，不是元素本身——排序中元素會被搬動，
   用位址算索引馬上就失效）。
2. **整頁的方向用「每一行都是直排」判斷**。漫畫頁面幾乎一定有幾行橫排（擬聲詞、頁碼、
   招牌，實測 12%），只要有一行，整頁的直排欄就改用「由左到右」，整句話就反了。
   現在改成多數決，和 `resolveAmbiguousOrientation` 一致。

10 頁真實漫畫，和正確答案逐段比對文字：

| 版本 | 完全一致 | 字相同但順序不對 |
|---|---|---|
| 原本 | 27 | 11 |
| 修好「同一欄」的判斷 | 28 | 10 |
| 再修好「整頁方向」的判斷 | **32** | **6** |

#### 分段的量測方式

**段落數本身不是好指標**：放寬門檻可以讓段落數變少，但正確復原的區塊也跟著變少、
合併過頭的變多。所以改用正確答案的區塊座標當基準（`tools/eval/evaluate_layout.py`）：

- **正確復原**：某個正確區塊裡的每一行，最後都落在「同一個」我們的段落裡，
  而且那個段落沒有混進別的區塊的行。
- **合併過頭**：我們的一個段落裡混到了兩個以上的正確區塊。

10 頁日文漫畫（正確答案 142 個區塊，其中 129 個有對應到我們的行）：

| 版本 | 段落數 | 正確復原 | 合併過頭 |
|---|---|---|---|
| ルビ 附著＋分群＋方向多數決 | 232 | — | — |
| ＋直排字級改用「欄長÷字數」、欄距改對稱 | **166** | **107** | 5 |

**直排的字級不能用框的寬度**：欄裡只要有「ー」「っ」或標點，框就會被拉窄，同一個對話框的
兩欄常常差兩倍以上，合併就被「字級差太多」擋掉（應該合併的配對中有 39% 是這樣被擋的）。
改成「欄長 ÷ 字數」之後這個問題就消失了。

改字級的同時發現兩個既有的 bug：`sortReadingOrder` 也用同一個函式當「是不是同一欄」的
容忍值（那裡應該用欄寬），而 `canMerge` 的距離計算是有方向性的（假設下一欄在左邊）——
改成分群之後任意兩行都會互相比較，這個假設就不成立了，現在一律用對稱的算法。

還沒解決的：12 個區塊仍被切開（對白 5、擬聲詞 4、標題 2、旁白 1），5 個合併過頭。

參考答案。視覺模型知道哪些字在同一個對話框裡，所以它的**分段**是很好的對照組。

#### ルビ 的顯示

Qt 的 rich text **不支援 `<ruby>`**（實測：讀音變成同一行的普通文字，高度也沒有增加，
見 `tests/integration/result_window_test.cpp` 的 `QtRichTextTest`）。
所以結果視窗要自己畫：把 `{本文|讀音}` 解析成一段一段，用 `QTextLayout` 排本文，
再用小一號的字把讀音畫在對應那幾個字的正上方，行高留出讀音的空間。

#### 橫直排判斷
- **自動**：逐個文字框判斷。如果是 CJK 文字，而且框的高度大於寬度的 1.5 倍，就視為直排。直排區塊會先旋轉圖片再辨識（manga-ocr 不需要旋轉）。
- **手動**：可切換「自動／強制橫排／強制直排」，也可以綁定快捷鍵。
- 漫畫同一頁常同時有直排對白和橫排旁白，所以一律逐區塊判斷。

#### 語言判斷（自動模式）
1. 偵測出的每一行，都用主模型（日文＋英文）和韓文模型各辨識一次（兩個模型用同一個偵測結果）。
2. 整個透鏡一起決定用哪個模型：數「韓文模型分數較高、而且結果有韓文字母」的行，和「主模型分數較高、而且結果有假名或漢字」的行，前者比較多就整個透鏡用韓文模型的結果，否則用主模型的結果。M0-11 用真實截圖確認，這個規則在日文、英文、韓文都選對了模型（見上方「M0-11 的評測結果」）。原本「主模型分數低於門檻才改用韓文模型」的做法不可行：PP-OCRv6 讀韓文時，會給亂讀的結果很高的分數。
3. 兩個模型都跑會讓辨識時間加倍，所以判斷出來的語言要記住：透鏡沒有移動、畫面也只是局部變化時沿用，只跑選定的模型；透鏡移動或畫面整個換掉時才重新判斷。
4. 依字元判斷每個區塊的語言：有韓文字母是韓文；有假名或漢字是日文（來源語言不包含中文，所以漢字一律當作日文）；其餘拉丁字母是英文。
5. 手動指定語言時，直接跳過第 1～4 步，只用對應的模型辨識。

#### 合併段落
- 依照距離、對齊方式、字高相近程度，把多行合併成一個區塊（一個對話框或一段段落）。**每個區塊就是結果視窗中的「一組」。**
- 各語言的換行接合規則：
  - 英文：接上空格；行尾被斷字的單字（`trans-` / `lation`）要接回去。
  - 日文：直接相連。
  - 韓文：接上空格。
- 碰到透鏡邊緣、被切掉一部分的區塊，預設忽略（可以在情境模式中關閉）。這樣可以避免捲動網頁時產生殘缺的句子。

#### 閱讀順序
- 橫排：由上到下、由左到右。
- 日文漫畫：直排欄位由右到左，區塊由上到下。
- 韓文條漫：由上到下。

#### M0-12 的評測結果

同一批原文（90 張真實截圖裡的 838 個區塊，去掉純數字和單一符號）送到四個引擎，譯文都經過 OpenCC 的
`s2twp`；再由你盲評 54 段（9 個分類各 6 段，不顯示引擎名稱、每段順序都不同），1～5 分。
工具和完整報告見 `tools/eval/README.md` 的「翻譯評測」（報告含有截圖裡的文字，只放在本機）。

| 引擎 | 盲評平均 | 日文 | 英文 | 韓文 | 每頁耗時 | 費用 |
|---|---|---|---|---|---|---|
| Gemini 3.5 flash-lite | **4.46** | 4.17 | **4.67** | **4.56** | **1.4 秒** | 免費額度內 |
| Claude Haiku 4.5 | 4.39 | **4.67** | 4.22 | 4.28 | 1.9 秒 | 838 段約 0.4 美元 |
| HY-MT2 7B（本機，Ollama） | 4.13 | 4.22 | 4.39 | 3.78 | 1.6 秒 | 免費 |
| Google（非官方端點） | 3.46 | 3.44 | 3.11 | 3.83 | 2.0 秒 | 免費 |

- **三個 LLM 之間沒有統計上的顯著差異**（54 段的配對比較，95% 信賴區間都包含 0）；
  **Google 顯著最差**（比 Gemini 低 1.00±0.37 分、比 Claude 低 0.93±0.44 分）。
- **Google 最弱的是沒有上下文的短字串**，而遊戲介面和漫畫正好很多：
  `ロード`（讀取）→「路」、`DONG`→「董」、`Shif`（按鍵提示）→「席夫」、`유튜브 라이브`→「優酷直播」。
  它的批次沒有問題（一頁的段落用換行合併送出，抽驗 18 頁全部對齊）。
- **免費的雲端 LLM 額度很小**：Gemini 3.6 flash 的免費層是「每天 20 次請求」，90 頁根本跑不完；
  flash-lite 才夠。產品不能假設使用者有可用的免費 LLM 額度。
- **本機 LLM 速度和雲端同一個量級**：HY-MT2 品質接近雲端 LLM，一頁約 1.6 秒（RTX 4070）。
  但它要占用 5.5 GB 顯示記憶體，會和遊戲搶資源，所以遊戲情境仍然預設用雲端（見第 5 節）。
- **連本機服務一定要用 `127.0.0.1`，不要用 `localhost`**：在 Windows 上 `localhost` 會先試 IPv6
  再退回 IPv4，每個請求多花約 2 秒（實測 2.2 秒對 0.15 秒）。一開始量到「本機 LLM 一頁 6.9 秒」
  幾乎都是這個連線成本。C++ 版（M2）要直接用 127.0.0.1，並重複使用同一條連線。
- **本機 LLM 的解碼受限於記憶體頻寬**，GPU 使用率看起來不高是正常的：每產生一個 token 都要把
  整個模型的權重讀過一遍。同時送多個請求可以讓權重只讀一次服務多個序列，吞吐量從 4.6 token/秒
  提高到 48 token/秒（平行 16 之後飽和）；修好連線之後，一頁只需要平行 4 就夠。
- **對齊**：LLM 偶爾會漏一段或輸出壞掉的 JSON（各一頁）。照 4.5 的做法「重試 → 逐段重送 →
  不要 JSON 只要譯文」處理後，四個引擎都是 838 段全部成功。
- **ルビ 標記**：`{本文|讀音}` 四個引擎都保留（3/3），但 Google 和 Gemini 會把讀音也翻成中文
  （フーダン→「復旦」），LLM 比較能理解標記的用意。
- **沒翻的段落**：書名號裡的作品名常保留原文（Claude 13 段、Gemini 23 段、HY-MT2 17 段），
  這是可接受的行為；HY-MT2 另外會留下部分擬聲詞。

**選定**：預設引擎鏈是「LLM（使用者填金鑰）→ Google」。漫畫和遊戲情境特別依賴 LLM 的上下文理解，
沒有金鑰時才用 Google。本機 LLM 當作離線或隱私優先的選項（速度夠，但會占用顯示記憶體），預設關閉。

#### 處理流程
1. **查快取**：以「引擎 + 來源語言 + 目標語言 + 正規化後的原文」為鍵。快取只存在記憶體中（LRU，約 1 萬筆）。
2. **引擎鏈**：依照情境模式設定的順序嘗試各引擎。遇到以下狀況時改用下一個引擎：網路錯誤、HTTP 429、回應格式錯誤、數量對不上。
3. **暫停失敗的引擎**：同一個引擎連續失敗 3 次，就暫時跳過 5 分鐘。
4. **對齊檢查**：譯文數量必須和原文數量相同。
   - 可以一次送出句子陣列的 API，天生就會對齊。
   - Google 非官方端點用換行把多段合併送出，回來後再切開並檢查數量；數量不對就改成逐段送出。
   - LLM 要求輸出等長的 JSON 陣列；解析失敗或數量不對時，改成逐段重翻。
5. **轉成台灣繁體**：所有譯文都經過 OpenCC 的 `s2twp` 設定（簡體轉繁體，並轉換成台灣慣用詞）。
6. **非官方端點限流**：每秒最多 1 個請求，降低被封鎖的風險。

#### 實作（M1-06）

`core/translation_service` 把這個流程串起來，各部分都可以單獨測試：

| 模組 | 負責 |
|---|---|
| `core/translator.h` | `ITranslator`、`TranslateRequest`、`TranslatorError` |
| `core/translation_cache` | 原文正規化和 LRU 快取 |
| `core/translator_chain` | 引擎順序、失敗計數、暫停 |
| `core/translation_alignment` | 從回應取出陣列、檢查對齊、逐段重送 |
| `core/opencc_converter` | `s2twp`（介面是 `ITextConverter`，測試時換成假的） |
| `core/translation_service` | 上面五個的組合 |

幾個實作上的決定：

- **快取以「段」為單位**，不是整批。畫面上只有一個對話框改變時，其餘各段仍然命中。
- **快取的鍵包含引擎**，所以換引擎不會沿用另一個引擎（可能比較差）的譯文；查詢時依照引擎鏈的順序找，
  首選引擎的結果優先，它暫停時才用備援引擎留下的。
- **正規化只動空白**：去掉前後空白、中間連續的空白（含全形空白）合併成一個、去掉零寬字元。
  大小寫不動，因為全大寫的遊戲介面和一般句子可能要翻得不一樣。
- **沒有字母的段落不送出**（`110/110`、`00:35`）：翻了也是原樣回來，不如省下時間和費用。
  判斷方式就是 4.4 的語言判斷回傳 Unknown。
- **同一個畫面上重複的文字只送一次**（例如兩個一樣的按鈕）。
- **只有「回應格式錯誤」才重試**：網路錯誤、額度用完、使用者取消都直接換下一個引擎，
  不在同一個壞掉的引擎上浪費時間和金錢。
- **暫停結束後重新給三次機會**，而不是一失敗就又被停掉。
- **譯文存進快取前就先轉成繁體**，取出來就是最終結果。

**OpenCC 的部署**：vcpkg 只安裝程式庫和字典，`cmake/Opencc.cmake` 負責把 `s2twp` 用得到的
5 個檔案複製到執行檔旁邊的 `opencc\`。vcpkg 的 opencc 有兩個包裝問題要繞過：匯出的相依目標中有一個
叫 `RapidJSON` 的目標（rapidjson 只有標頭檔、沒有程式庫），以及靜態版沒有定義
`Opencc_BUILT_AS_STATIC`（少了它，標頭會把函式宣告成 `__declspec(dllimport)`）。

#### Google 非官方引擎（M1-07）

`net/google_translator`。沒有金鑰時的預設引擎，也是引擎鏈的最後一道。

- **一批一個請求**：段落用換行接起來當作 `q`，回來的譯文再用換行切開。端點偶爾會把換行吃掉，
  這時數量就對不上，改成逐段重送（`core/translation_alignment`）。**不重試整批**：
  這個端點沒有隨機性，重送只會多等一秒。
- **逐段重送時要把譯文裡的換行壓成空格**，否則接回去又會多出一段。
- **每秒最多一個請求**（`net/rate_limiter`）：計算「還要等多久」和真正的等待分開，
  測試才不必真的睡。等待可以被取消，使用者移動透鏡時不用等滿一秒。
- **一定要送 `User-Agent`**，否則端點回 403。
- **錯誤對應**：連不上和 5xx 是 `Network`、429 是 `RateLimited`、看不懂的回應是 `BadResponse`，
  引擎鏈據此決定要不要換下一個引擎。

回應是巢狀陣列，第一層的第一個元素是一段一段的譯文，長句子會被切成好幾段，要全部接起來：
`[[["你好，","Hello, ",…],["世界","world",…]],…]`。

測試用的是**真的向端點要過一次、錄下來的回應**（`tests/data/net/google_*.json`，CT-01），
再加上 `tools/translate_cli` 對真正的端點手動實測。

#### LLM 提示詞（草案）
- **系統訊息**：你是翻譯引擎。把 `segments` 中的每個字串翻譯成台灣繁體中文，保留語氣和角色口吻，專有名詞依照 `glossary` 翻譯。只輸出和 `segments` 等長的 JSON 字串陣列，不要加任何說明。
- **使用者訊息**：`{"source_lang": "...", "context": [...], "glossary": {...}, "segments": [...]}`

#### OpenAI 相容格式的 LLM 引擎（M1-08）

`net/openai_translator`。同一個格式可以接 OpenAI、Gemini、DeepSeek、OpenRouter，以及本機的
Ollama、llama.cpp、LM Studio，所以只要一份實作，使用者只需要填「網址、模型名稱、金鑰」。

- **提示詞沿用 M0-12 實測過的版本**（盲評 4.13～4.46 分），包含 ルビ 標記的說明。
- **一個畫面的段落一次送出**，要求輸出等長的 JSON 陣列。
- **三層退路**：整批 → 整批重試一次 → 逐段重送，而且**逐段時不要 JSON、只要譯文**
  （模型偶爾會在譯文裡用沒有逸出的引號，JSON 就壞了）。M0-12 實測四個引擎都靠這層補完。
- **串流**：`stream: true` 時邊收邊解析（`net/sse` 組回被切開的行，
  `core/translation_alignment` 的 `parseJsonArrayPrefix` 取出已經完整的段落），
  收完一段就可以先填進結果視窗，不必等整批（4.7「邊翻邊顯示」）。
- **本機服務的網址自動把 `localhost` 換成 `127.0.0.1`**（M0-12：否則每個請求多約 2 秒）。
- **錯誤訊息不含回應內容**：回應裡有截圖中的文字，只留狀態碼和 API 自己的錯誤說明。
- **4xx（金鑰錯誤、模型名稱錯誤、被擋）是 `Rejected`**，不重試；重送同樣的內容不會變好。
  429 是 `RateLimited`、5xx 和連不上是 `Network`、看不懂的回應才是 `BadResponse`（會重試一次）。

測試用的是**真的向本機 Ollama（hy-mt2）要過一次、錄下來的串流和非串流回應**
（`tests/data/net/openai_*`，CT-02）。實測結果：

| 情境 | 結果 |
|---|---|
| 本機 hy-mt2，9 段（約一頁） | 0.6～3.7 秒（重複送同樣的內容時 Ollama 有快取），和 M0-12 的 1.6 秒同一個量級 |
| 本機 hy-mt2，2 段 | 0.8 秒 |
| **同時有遊戲在用 GPU** | 同樣的請求要 20～60 秒（Python 直接呼叫也一樣慢，不是程式的問題） |
| 雲端 gemini-3.5-flash-lite，5 段 | 1.3 秒，逐段串流出來 |
| 金鑰或模型名稱錯誤 | 回報「請求被拒絕」而且不重送 |

`{本文|讀音}` 的標記在雲端實測中完整保留，而且本文和讀音分別翻譯
（`{本気|マジ}` →「{認真|真的}」、`{未来|あした}` →「{未來|明天}」），
和 4.5「振り仮名的翻譯」的要求一致。

**遊戲和本機 LLM 搶 GPU 的代價比預期大得多**：實測慢了 10～20 倍，等於不能用。
這證實了 M0-12 的判斷（第 6 節：遊戲情境預設用雲端），而且要更進一步——
**遊戲情境不應該只是「預設」用雲端，選了本機 LLM 時還要提醒使用者**（M1-12 的設定畫面）。

#### 振り仮名的翻譯

另有含義的ルビ（見 4.4）要和本文一起翻譯，兩邊的譯文都要保留：

- **送出的格式**：用 `{本文|ルビ}` 標出來，例如 `{本気|マジ}で戦うぞ`。
- **LLM 引擎**：提示詞說明這個標記的意思（左邊是字面、右邊是角色唸出來或實際代表的意思），要求譯文在對應的位置保留同樣的標記，例如 `我要{認真|玩真的}打一場`。程式再把它拆回本文和ルビ。解析失敗時，改用下面一般翻譯引擎的做法。
- **一般翻譯引擎**（Google、DeepL 等）看不懂這種標記，送過去會讓對齊檢查一直判定「標記數量不同」，
  所以**送出前先把標記還原成只有本文**（`core::stripRubyMarkup`），對齊檢查也關掉 ルビ 那一項：本文照常翻譯（不含標記），另有含義的ルビ詞另外單獨翻譯，再以「本気（マジ）→ 認真（玩真的）」的形式附在這個區塊的譯文後面。效果比 LLM 差，漫畫的情境模式建議使用 LLM 引擎。
- **對齊檢查**：LLM 回應中的標記數量必須和原文相同，否則視為格式錯誤（和 4.5 的對齊檢查一樣處理）。

#### 金鑰保管
- 使用者填入的 API 金鑰用 DPAPI（`CryptProtectData`）加密後，存進設定檔。
- 倉庫中不包含任何金鑰。設定檔範例中的金鑰欄位一律留空。

### 4.6 處理管線（M1-09）

`core/pipeline` 把一次處理從頭走到尾，`core/pipeline_worker` 負責排隊和執行緒。

```
擷取的畫面 ─▶ IOcrService ─▶ 排閱讀順序、合併段落 ─▶ 去掉碰到邊緣的 ─▶ 判斷語言
                                                                        │
                        結果（原文／譯文成組）◀── TranslationService ◀───┘
```

- **OCR 透過 `IOcrService` 注入**：core 不認得 OpenCV，也不該認得模型。
  `ocr/ocr_service` 是產品用的實作（BGRA → BGR、文字框 → 外接矩形和橫直排）。
- **語言整片一起判斷**：單一段落常常太短（M0-11）。使用者可以手動指定，指定了就不自動判斷。
- **上下文**：把最近幾組原文和譯文帶給 LLM（`TranslateRequest::context`）。
- **和上一次一樣就標記 `unchanged`**：畫面閃了一下又回到原樣時不必新增歷史卡片。
  每個透鏡各自記住自己的上一次。
- **翻譯失敗時仍然顯示原文**，並附上失敗原因；使用者自己取消不算失敗。

**佇列和取消**（design.md 3.3）：

- 推論依序執行，避免多個透鏡同時搶 GPU。
- **排隊中的工作每個透鏡只留最新的一件**：中間那幾件一定已經過時（畫面或透鏡位置變了）。
- **同一個透鏡送來新工作時，進行中的那件會被取消**，`std::stop_token` 一路傳到 OCR 和 HTTP。
- **被取消的結果不會送回去**。另外每個結果都帶著流水號，UI 再依 `AutoTrigger` 的流水號判斷一次。
- 結果的回呼在工作執行緒上，UI 端負責排隊回到 UI 執行緒（Qt 的 queued signal）。

端到端測試（IT-08）用真的測試視窗顯示英文句子、真的擷取、真的 OCR 模型，搭配假翻譯引擎，
確認「原文／譯文成組」完全正確。

### 4.7 結果視窗（第一階段）

```
┌─ 翻譯結果 ───────────────────── [置頂] [清除] ─┐
│ ── 14:32:05 · 透鏡 1 · 日文 ────────────────── │
│  おい、待てよ！                                 │  ← 原文（淡色、較小）
│  喂，等一下！                                   │  ← 譯文（主色）
│                                                 │
│  そんなこと言われても困るんだけど……            │
│  你這樣說我也很困擾啊……                        │
│ ── 14:32:41 · 透鏡 1 · 英文 ────────────────── │
│  Wait, you're not serious, are you?             │
│  等等，你不是認真的吧？                         │
│                                  [↓ 回到最新]   │
└─────────────────────────────────────────────────┘
```

- **一組** = 一個文字區塊（原文一行、譯文一行）。
- **一張卡片** = 同一次翻譯產生的所有組，標示時間、來源透鏡和語言，組的順序依照閱讀順序。
- **只放新內容**：新卡片只包含「和同一透鏡的上一張卡片相比，新出現的文字區塊」。如果完全沒有新內容，就不新增卡片。這樣捲動網頁時不會重複記錄同樣的句子。
- **邊翻邊顯示**：原文先出現並標示「翻譯中…」，譯文回來後再填入（LLM 串流時逐組填入）。
- **捲動**：新卡片加在最下方。使用者往上捲時不會被拉回底部，而是出現「回到最新」按鈕。
- **容量上限**：記憶體中最多保留 500 張卡片，超過時丟棄最舊的。關閉程式就全部清除。
- **位置**：獨立視窗，由使用者自由擺放。程式會記住上次的位置和大小（這屬於設定，不是歷史紀錄）。
- **其他**：可切換「置頂」；字級可以調整；深色／淺色主題跟隨系統；排除擷取。
- **漫畫的小字和擬聲詞**（見 4.4）：
  - 另有含義的ルビ：原文和譯文都以ルビ的形式顯示，小字標在對應的詞上方，例如譯文「認真」上方標「玩真的」。
  - 旁註和擬聲詞各自成組，前面分別標示「註」和「擬聲詞」。
  - 字級分三級還原：小字（ルビ、旁註）、一般、大字（擬聲詞，以及比同一畫面中位數大 1.5 倍以上的行）。
- **實作**：`QListView` 加上自訂的 delegate，只繪製畫面上看得到的項目（`ui/result_window`、
  `ui/history_model`、`ui/card_delegate`，M1-11）。一列是一張卡片，卡片的高度由 delegate
  依內容算出來。
- **歷史紀錄**（`core/history`，M1-10）：「只放新內容」比對的是同一個透鏡**上一次的結果**，
  不是上一張卡片。卡片本身已經被過濾過，拿它來比對的話，被濾掉的句子下一次又會變成「新的」。
- **位置和大小**：拖動視窗時不會每個像素都存一次設定，停下來 0.5 秒後才通知呼叫端去存。

### 4.8 覆蓋層與風格還原（第二階段）

- **覆蓋層視窗**：每個透鏡一個，視窗樣式為 `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`。整個視窗都讓滑鼠穿透，並且排除擷取。
- **繪製**：Direct2D + DirectWrite，支援直排（例如 `DWRITE_READING_DIRECTION_TOP_TO_BOTTOM`），標點符號會使用直排專用字形。
- **背景還原**：
  - 純色背景：取樣周圍顏色填補。
  - 複雜背景：用 LaMa 修補模型（ONNX）。沒有 GPU 時一律改用純色填補。
- **風格估計**：

| 屬性 | 做法 |
|---|---|
| 文字顏色 | 對文字遮罩內的像素做顏色分群 |
| 描邊顏色 | 分析文字邊緣的第二種主要顏色 |
| 字級 | 以行為單位，由行高（直排是欄寬）推算，保留同一個畫面中各行之間的大小比例；再依譯文長度自動縮放以塞進原本的範圍 |
| 振り仮名 | 另有含義的ルビ，譯文也用小字畫在對應的詞旁邊（直排在右側、橫排在上方），大小比例和原文相同 |
| 粗細 | 估算筆畫寬度 |
| 字型 | 分類成黑體、明體、圓體、手寫體，再對應到內建字型；使用者可以自訂對應 |

- **內建字型**：Noto Sans TC、Noto Serif TC、jf open 粉圓（皆為 OFL 授權，可以隨程式發布）。
- **畫面變化時**：立即隱藏覆蓋層，內容穩定後再從快取快速補回。這樣捲動網頁時不會出現錯位的譯文。
- **擬聲詞和藝術字**：預設不覆蓋原圖，譯文用小字標在旁邊，同時在結果視窗中顯示（M4-05 評估是否提供覆蓋的選項）。

| 內容 | 位置 |

## 5. 硬體等級與效能預算

程式啟動時偵測硬體，自動選擇預設等級，使用者也可以手動覆寫。

| 元件 | 有獨立顯卡 | 只有內顯 | 純 CPU |
|---|---|---|---|
| OCR | PP-OCRv6 medium，DirectML | PP-OCRv6 small，DirectML | PP-OCRv6 small，透鏡大小約 0.3 秒（medium 要 1.1 秒，v5 server 要十幾秒，不能用） |
| 漫畫 OCR | 編碼器 23 ms（DirectML）＋解碼 | 可用 | 編碼器 0.26 秒＋解碼；還沒有 KV cache 時每個對話框約 0.5 秒（M0-15 實測） |
| 翻譯 | 雲端 LLM（本機 LLM 是離線選項，M0-12 實測一頁 1.6 秒，但占用 5.5 GB 顯示記憶體） | 雲端 | 雲端 |
| 背景修補 | LaMa | 視效能而定 | 純色填補 |

**處理延遲預算**（以 RTX 4070 粗估）

| 步驟 | 目標 |
|---|---|
| 擷取、裁切、變化偵測 | < 5 ms |
| 等待穩定 | 300～600 ms（刻意等待） |
| OCR | < 150 ms（M0-14 實測 283 ms，見下方） |
| 翻譯（網路） | 200～1000 ms（M0-12 實測一頁 9.3 段：Gemini flash-lite 1.4 秒、Claude Haiku 1.9 秒、Google 2.0 秒，都要逐組串流顯示） |
| 翻譯（本機 8B LLM） | 0.5～3 s（逐組串流顯示） |
| **從停止移動到出現結果** | **約 1～2 s** |

**M1-03 的最佳化結果**（Release 版，RTX 4070；透鏡大小的畫面 720×405、7 行文字）

| 做法 | 偵測 | 辨識 | 合計 |
|---|---|---|---|
| M0-14：逐行辨識、輸入大小隨圖片變 | 59 ms | 224 ms | 283 ms |
| M1-03：批次辨識、固定輸入大小 | 20 ms | 85 ms | **106 ms** |

- **批次辨識**：DirectML 上每次呼叫的固定成本很高（每行 25～40 ms，和模型大小幾乎無關），
  所以同一張畫面的文字行一次送進模型。寬度先補齊到 8 種固定級距再分組，所以加大批次不會
  多補 0；一批的張數由寬度預算決定（窄的一次 64 張，最寬的 10 張）。真實 4K 截圖（21 行）
  的辨識也從 196 ms 降到 107 ms。
- **固定輸入大小**：一個推論工作階段只有「第一次看到的輸入大小」跑得快，之後每換一種大小，
  那個大小的**每一次**推論都慢 3～5 倍（12 ms → 41 ms），而且不會恢復。透鏡可以調整大小，
  所以把畫面等比例縮放後補邊到固定大小（長寬對齊到 32 的倍數，否則模型內部的 Resize 在
  DirectML 上會失敗）。代價是透鏡大小的畫面從 12.6 ms 變成 20 ms，但換來穩定。

  **原因**（用 `tools/shape_bench` 直接對模型餵不同形狀量測）：

  | 做法 | 載入 | 第一次推論 | 之後每次 |
  |---|---|---|---|
  | 不宣告形狀（目前） | 120 ms | 227 ms | 3.3 ms |
  | 建立工作階段時就宣告形狀 | 387 ms | 3.6 ms | 2.3 ms |

  DirectML 在第一次遇到某個形狀時才把運算編譯成 GPU 的指令，而且只保留一份。換成別的形狀後，
  新形狀的**每一次**推論都要重做這件事，所以永遠慢；換回原本的形狀又會變快。
  CPU 完全沒有這個現象（大的形狀慢、小的快，和順序無關），所以這是 DirectML 專屬的行為。
  官方文件也說「形狀在建立工作階段時就知道，DirectML 才能先最佳化」。

  **還沒採用的進一步最佳化**：用 ORT 的 `AddFreeDimensionOverrideByName` 在建立時宣告形狀，
  可以把 227 ms 的編譯移到載入階段（使用者的第一次翻譯就不會卡），穩定後還快 30%。
  但宣告之後只要餵進不同的形狀，程序會直接當掉（0xC0000409），所以要先確保只會用一種形狀。
  辨識模型的形狀本來就會變（批次大小 × 寬度級距），不適用；偵測模型固定輸入後適用，M1 後期再評估。
- **啟動時先暖機**：載入模型後用假的畫面各跑一次偵測和辨識，把 DirectML 的編譯成本移到啟動階段。
  使用者的第一次翻譯從 584 ms 降到 123 ms，代價是載入多花 425 ms（本來就在背景進行）。
- **沒有 GPU 時改用 small 模型**（`ocr/model_choice`）：medium 在 CPU 上要 1.1 秒、small 只要 0.3 秒；
  代價是日文遊戲的字元錯誤率從 3.1% 升到 9.1%（M0-11）。韓文不論裝置都用韓文辨識模型。
- **準確度**：90 張真實截圖上，批次和逐行的字元錯誤率完全相同；合成測試集 32 行中有 2 行不同，
  都在模型本來就讀不出來的韓文圖上。逐行辨識的結果仍和 PaddleOCR 官方版完全一致，
  `tools/eval/check_ocr_equivalence.py` 每次都會量測這兩者的差異。

**OCR 實測**（M0-14，Release 版，RTX 4070＋i5-13600KF；透鏡大小的畫面 720×405、7 行文字；括號內是偵測＋辨識）

| 模型 | CPU | DirectML |
|---|---|---|
| PP-OCRv6 medium | 1095 ms（509＋586） | 283 ms（59＋224） |
| PP-OCRv6 small | 317 ms（162＋155） | 207 ms（27＋180） |
| PP-OCRv6 tiny（不支援日文） | 59 ms（36＋24） | 96 ms（23＋73） |
| PP-OCRv5 server | 10.7 s（1.8 s＋8.9 s） | 377 ms（95＋282） |
| PP-OCRv5 mobile | 351 ms（128＋223） | 218 ms（27＋192） |
| 韓文（v5 server 偵測＋韓文辨識） | 1.9 s（1.8 s＋142） | 356 ms（94＋262） |

- DirectML 的偵測很快（23～95 ms），但**辨識每行約 25～40 ms，而且和模型大小幾乎無關**：瓶頸是「一行呼叫一次、每行寬度都不同」的固定成本，不是運算量。所以目前超過 150 ms 的預算。M1-03 要把同一張畫面的多行合成一批，寬度補齊到固定級距（見 4.4 的 DirectML 限制）。
- tiny 在 DirectML 上反而比 CPU 慢：模型太小，呼叫 GPU 的成本比運算還大。
- 模型載入：CPU 0.1～0.6 秒，DirectML 0.3～0.8 秒，只在啟動時發生一次。
- 量測方式：`tools/eval/check_ocr_equivalence.py` 產生的 `build/ocr_eval/report.md`；每張圖片跑 5 次（CPU 2 次），第一次暖機不計。

**閒置時的資源預算**：透鏡開著但畫面沒有變化時，CPU 使用率應低於 1%。

- 做法：系統只在畫面改變時才送新畫面，沒有新畫面就完全不取樣。取樣時在 GPU 上用 mipmap 縮小後才讀回，讀回的資料量只有原圖的幾十分之一。
- M0-07 實測（Release 版）：螢幕上其他地方持續變化時，整台電腦約 0.17%，換算成單一核心約 3.4%。
- 剩下的成本來自「螢幕上任何地方有變化都會取樣」，M1-17 會改成只在變化區域和透鏡重疊時才取樣。

## 8. 發布

- **建置**：用 GitHub Actions 的 Windows 環境自動建置（公開倉庫免費）。
- **安裝程式**：基本安裝包只包含程式本體和 ONNX Runtime（DirectML 版），不包含 CUDA。
- **模型**：放在 Hugging Face 或 GitHub Releases。使用者第一次使用某個情境模式時才下載，下載後用 SHA-256 驗證。
- **程式碼簽章**：向提供開源專案免費簽章的服務申請（例如 SignPath）。這能減少 SmartScreen 警告和防毒軟體誤判。
- **非官方端點失效**：靠引擎鏈自動備援；修正時盡快發布更新版本。
- **第三方授權聲明**：發布時附上 `THIRD_PARTY_NOTICES`，列出所有元件、模型和字型的授權。

## 10. 風險與對策

| 風險 | 對策 |
|---|---|
| 非官方端點失效或被限流 | 引擎鏈自動備援、暫停失敗的引擎、主動限流、快速更新 |
| 免費的雲端 LLM 額度很快用完 | M0-12：Gemini 3.6 flash 免費層每天只有 20 次請求。介面要顯示額度用完的錯誤，並自動換下一個引擎；說明文件標示各引擎的免費額度 |
| LLM 回傳的段落數量對不上或格式壞掉 | M0-12 實測各出現一次。三層退路：重試 → 逐段重送 → 不要 JSON 只要譯文（4.5） |
| OCR 讀不好特殊字型 | M0-11 用 90 張真實截圖評測：遊戲、網頁的 CER 在 3% 以下，漫畫對白用 manga-ocr 在 2% 左右；依情境選擇模型（見 4.4） |
| manga-ocr 在 C++ 中實作困難 | M0-15 已確認：ONNX 版本加上自己寫的解碼，結果和官方完全一致；C++ 版照 Python 版移植（M2-03） |
| 擬聲詞偵測不到（畫在圖上的大型藝術字） | M0-11 確認 comic-text-detector 的文字遮罩找得到日文、英文的擬聲詞；韓文只找到 38%，M2-16 再評估 |
| 擬聲詞辨識不出來 | M0-11：所有模型的 CER 都在 80% 以上，還沒有解法。M2-16 評估對照表比對、專門的模型，或只標出位置；對白的翻譯不受影響 |
| 把小字的本文誤判成ルビ，或漏掉ルビ | 依字的大小和位置判斷；M0-10 標註真實截圖中的ルビ，M2 評測正確率 |
| C++ 的 OCR 前後處理和 Python 版結果不一致 | M0-14 已逐項比對並確認一致（見 4.4）；之後修改 OCR 程式碼時都要重新跑一致性檢查 |
| OCR 速度超過預算（M0-14：透鏡大小 283 ms，預算 150 ms） | M1-03 已解決：批次辨識＋固定輸入大小後 106 ms（見第 5 節） |
| 推論工作階段換了輸入大小就永久變慢（M1-03 實測 3～5 倍） | 偵測固定輸入大小、辨識補齊到固定的寬度級距；之後加新的模型或裝置時要重新量測 |
| DirectML 進入持續維護，ONNX Runtime 的 DirectML 版不再更新 | Windows ML 的 API 相同，需要時改用；M0 先用 DirectML，因為它支援所有 DirectX 12 顯示卡 |
| 遊戲畫面永遠不會靜止 | 「只看文字區域」的兩層偵測，加上快捷鍵手動觸發 |
| 分層視窗縮放時閃爍 | M0-05 實測（含 150% 縮放）沒有閃爍，維持使用系統的拖動和縮放；之後若在別的環境出現，備案是自己處理滑鼠 |
| 高更新率螢幕造成 CPU 負擔 | 擷取節流、在 GPU 上縮圖後才讀回 |
| 本機 LLM 和遊戲搶顯示卡記憶體 | 遊戲模式預設使用雲端引擎 |
| 防毒軟體誤判 | 程式碼簽章、不注入其他程式、開源透明 |
| DPI 或多螢幕座標錯誤 | M0-08 的整合測試在 150% 縮放下通過；多螢幕和其他縮放比例還沒測，列在手動測試矩陣（execution-plan 5.9） |
| 模型無法轉成 ONNX 或無法在 DirectML 上執行 | PP-OCRv5、v6 和韓文模型都有官方 ONNX 版本，也都能在 DirectML 上執行（M0-14 確認）；manga-ocr 在 M0-15 確認 |
| 測試用的漫畫和遊戲截圖有版權，不能放進公開倉庫 | 真實截圖只放在本機（加入 .gitignore）；CI 使用開源字型合成的測試圖 |
| C++ 開發速度較慢 | 評測用 Python；UI 用 Qt；先完成 MVP 再擴充 |
