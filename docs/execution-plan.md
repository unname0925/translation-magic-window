# 執行計畫、待辦清單與驗證機制

> 對應設計文件：[design.md](design.md)
> 最後更新：2026-09-18

---

## 1. 執行原則

1. **先處理風險最高的部分。** M0 只做一件事：證明「可能讓整個計畫做不下去」的技術點都可行。不寫任何不確定能不能用的功能。
2. **先讓整條流程跑通，再逐步變強。** M1 用最簡單的元件，先做到「擷取 → OCR → 翻譯 → 顯示」從頭到尾都能跑，之後再把每個環節換成更好的版本。
3. **架構要能測試。** 邏輯放在 core，不依賴 Win32、Qt 和網路（見 design.md 3.2），這樣大部分的 bug 都能用單元測試抓到。
4. **每個里程碑結束時都有可以實際操作的成果**，並且通過該里程碑的驗收測試，才進入下一個里程碑。
5. **小步提交。** 一個任務一個分支，CI 全部通過才合併。每次合併前都做一次程式碼審查。

| 角色 | 負責 |
|---|---|
| **你** | 收集測試截圖、評分翻譯品質、在真實情境下手動測試、決定待決事項 |

任務大小：**S** = 半天以內；**M** = 1～2 天；**L** = 3～5 天（以實際開發時間粗估）。

## 3. 里程碑總覽

| 里程碑 | 可以實際操作的成果 | 離開條件 |
|---|---|---|
| **M0 技術驗證** | 一個透鏡：拖動後停下來，會自動把底下的畫面存成 PNG；C++ 能對一張圖片跑 OCR | 第 4 節 M0 的驗收項目全部通過，並選定模型 |
| **M1 第一階段 MVP** | 透鏡停在網頁或遊戲上，結果視窗會出現原文／譯文對照 | MVP 驗收測試和 1 小時耐久測試通過 |
| **M2 完整第一階段** | 漫畫直排、韓文、自動語言、情境模式、多種引擎 | 回歸評測的分數達標，並通過完整的手動測試矩陣 |
| **M3 基本覆蓋** | 譯文直接顯示在原文位置上 | 繪製結果的圖片比對測試通過 |
| **M4 風格還原** | 譯文的顏色、描邊、字級、字型接近原文 | 你在真實漫畫和遊戲上主觀評分及格 |
| **M5 發布** | 可以安裝的正式版本 | 在一台乾淨的 Windows 11 上安裝並完成測試 |

## 5. 驗證機制（找出 bug 的方法）

### 5.1 總覽

不同種類的 bug 由不同的層級負責抓，越下面的層級越便宜、執行越頻繁：

| 層級 | 抓得到的 bug | 什麼時候跑 | 失敗會擋住合併嗎 |
|---|---|---|---|
| 編譯期檢查 | 型別錯誤、未初始化的變數、可疑的寫法 | 每次建置 | 會 |
| 單元測試（UT） | core 的邏輯錯誤 | 每次建置、每個 PR | 會 |
| 記憶體錯誤檢查 | 越界存取、使用已釋放的記憶體 | 每個 PR（CI） | 會 |
| 翻譯引擎契約測試（CT） | 回應解析錯誤、對齊錯誤 | 每個 PR（使用錄製下來的回應） | 會 |
| 整合測試（IT） | 視窗、擷取、穿透、座標的錯誤 | 本機每次改到 platform 時；CI 能跑的就放 CI | 會 |
| 模型品質回歸 | OCR 準確度下降 | 每個 PR 跑合成測試集；本機跑私有測試集 | 下降超過門檻就會 |
| 效能與資源 | 變慢、記憶體洩漏、資源沒有釋放 | 每個里程碑結束時；改到熱點程式碼時 | 超過預算就會 |
| 線上端點檢查 | 非官方端點失效 | 每天自動執行 | 不會，只發出通知 |
| 手動測試矩陣 | 真實環境才會出現的問題 | 每個里程碑結束時 | 里程碑的驗收條件 |
| 執行期的自我檢查 | 使用者電腦上才出現的 bug | 一直開著 | — |

### 5.2 編譯期檢查

- 警告等級 `/W4`，並用 `/WX` 把警告當成錯誤；`/permissive-` 採用標準 C++ 的嚴格模式。
- CI 執行 MSVC 的靜態分析（`/analyze`）。
- CI 檢查 `clang-format` 格式，避免無意義的格式差異。

### 5.3 單元測試（GoogleTest）

測試對象是 core，以及不需要桌面環境的 platform 工具函式（例如編碼轉換）。所有會牽涉時間的邏輯，都用**假時鐘**控制，測試結果不受機器快慢影響。

**警報測試**：ASan 版會額外編譯一個「故意越界讀取」的測試，ASan 必須抓到。如果 ASan 版實際上沒有開啟 ASan，建置會直接失敗。這樣「ASan 測試全部通過」才代表真的沒有記憶體錯誤，而不是檢查機制根本沒在運作。

| ID | 對象 | 主要測試情境 |
|---|---|---|
| UT-01 | 狀態機 | 拖動中出現畫面變化不會觸發；停下後 settleMs 內畫面變化會重新計時；處理中畫面變化，結果會被丟棄；開始拖動時流水號加一；拖動中按手動觸發無效 |
| UT-02 | 變化偵測 | 相同畫面視為沒變；少量雜訊視為沒變；多出一行字視為有變；遊戲模式下，文字框外的閃爍會被忽略 |
| UT-03 | 合併段落與閱讀順序 | 用 JSON 描述的 OCR 框作為輸入，檢查輸出的段落和順序；英文斷字接回；日文直排由右到左；被邊緣切到的區塊會被過濾；ルビ的小字行要對應到正確的本文字元，不能混進本文 |
| UT-04 | 語言判斷 | 假名、韓文字母、純漢字、英文、混合文字 |
| UT-05 | 翻譯對齊 | LLM 回應的各種異常：多一段、少一段、夾雜說明文字、用 code block 包起來、JSON 壞掉。每種都要被正確處理，或觸發逐段重翻 |
| UT-06 | 引擎鏈 | 用假引擎依序模擬失敗，檢查是否改用下一個；連續失敗 3 次後暫停 5 分鐘（用假時鐘） |
| UT-07 | 快取與 OpenCC | LRU 淘汰順序；正規化後相同的原文會命中同一筆；已知詞彙能正確轉換（例如「软件」轉成「軟體」） |
| UT-08 | 歷史紀錄 | 只放新內容；沒有新內容時不新增卡片；超過 500 張時淘汰最舊的 |
| UT-09 | 設定檔 | 舊版本能正確遷移；壞掉的 JSON 會被備份並改用預設值；欄位缺少時會補上預設值 |
| UT-10 | 座標換算 | DPI 換算；透鏡有一部分超出螢幕時的裁切範圍；跨螢幕時選擇正確的螢幕 |

### 5.4 整合測試（需要桌面環境）

整合測試放在 `tests/integration/`，執行方式是 `cmake --workflow --preset integration`。一般的測試流程（debug、release、asan）不會執行它們，因為執行時會在螢幕上短暫顯示測試視窗，還會移動滑鼠。

測試用的視窗（`tests/integration/support/test_window.h`）會畫出「每個像素的顏色都由自己的座標決定」的圖案，所以從擷取結果就能反推出位置，座標偏移 1 個像素也會被發現。它也會記錄收到的點擊，用來測試穿透。

**測試真正的主程式**：`app_test.cpp` 在另一個程序中啟動實際會發布的 `TranslationMagicWindow.exe`，從外部用真實的滑鼠輸入和螢幕擷取檢查它。跨程序很重要，因為穿透的常見錯誤做法（`HTTRANSPARENT`）只在同一個執行緒內有效，在同一個程序裡測會誤判成正常。

- 主程式用 `--data-dir` 指定暫存資料夾啟動，測試結束後刪除，不會動到你的資料。
- 執行前必須先結束正在執行的主程式（單一執行個體），否則測試會直接失敗並說明原因。
- 會移動滑鼠和點擊，執行期間請不要操作滑鼠。每次點擊前都會確認位置是測試視窗或透鏡，結束後游標回到原位。

凡是「確認某個東西不存在」的測試（例如被排除的視窗沒有出現在擷取結果中），都要搭配**正向對照**：用同樣的方法檢查一個「應該存在」的東西，證明這個測試確實測得出差異。

**時間限制**：整合測試等待第一張畫面最多 5 秒（正式程式是 1 秒），單一測試超過 60 秒就判定失敗。放寬等待時間的原因是：M0-07 時觀察到，剛建置好的 ASan 版程式前幾次執行時，防毒軟體會讓整個程序暫時變慢，導致 4 個測試逾時失敗。之後用「重複直到失敗」模式連續跑 5 輪、共 50 次都通過，排除了競爭條件。如果之後又出現偶發失敗，先用 `ctest --repeat until-fail:N` 重現，不要直接放寬時間限制。

| ID | 驗證內容 | 做法 | 測試（`tests/integration/`） |
|---|---|---|---|
| IT-01 | 排除擷取 | 把真正的透鏡放在測試圖案上，擷取整個透鏡範圍，結果必須和圖案逐像素相同 | `AppTest.LensIsExcludedFromCapture`、`ScreenCaptureTest.ExcludedWindowDoesNotAppear` |
| IT-02 | 中間穿透 | 用 `SendInput` 點擊透鏡中間，以及穿透範圍最邊緣的像素，測試目標必須收到點擊，座標也要正確 | `AppTest.ClicksInsideLensReachWindowBelow` |
| IT-03 | 邊框可拖動 | 拖動把手和右下角，透鏡的位置和大小要改變完全相同的量，測試目標不能收到點擊 | `AppTest.DraggingHandleMovesLensWithoutClickingBelow`、`AppTest.DraggingCornerResizesLens` |
| IT-04 | 單一執行個體 | 啟動第二個執行個體，它必須自行結束，並讓第一個執行個體顯示透鏡；結束後可以再次啟動 | `AppTest.SecondInstanceExitsAndShowsTheLens`、`AppTest.InstanceCanStartAgainAfterExit` |
| IT-05 | 座標正確 | 擷取測試圖案的一部分，每個像素的顏色都要對應到正確的座標 | `ScreenCaptureTest.SubRegionCoordinatesAreExact` |
| IT-06 | 擷取節流 | 統計每秒的回呼次數，不能超過設定值 | `ScreenCaptureTest.SystemThrottlesFrameRate` |
| IT-07 | 不含游標 | 游標停在擷取範圍內時，擷取結果必須和圖案完全相同 | `ScreenCaptureTest.CursorIsNotCaptured` |
| M0 端到端 | 自動觸發和存檔 | 透鏡底下換成測試圖案後，主程式自動存出的 PNG 必須剛好是擷取範圍的內容 | `AppTest.AutoSavedCaptureMatchesContentUnderLens` |
| IT-08 | 端到端 | 測試目標顯示已知的英文句子，搭配假翻譯引擎，結果視窗的資料要和預期完全一致。測試視窗顯示文字的功能到 M1-09 有 OCR 時再加 | M1-09 |

**確認測試本身有效（突變測試）**：新增整合測試時，要故意把對應的功能改壞一次，確認測試真的會失敗、失敗訊息也指向正確的原因。M0-08 的結果：

| 故意改壞的地方 | 失敗的測試 |
|---|---|
| 透鏡不排除擷取 | IT-01；端到端測試（只差內側抓取區 1/255 的透明度也抓得到） |
| 透鏡中間改成用 `HTTRANSPARENT` 穿透 | IT-02 |
| 把手和角落不能拖動 | IT-03 的兩個測試 |
| 不檢查單一執行個體 | IT-04 |
| 擷取時包含游標 | IT-07 |
| 自動存檔的範圍偏移 1 個像素 | 端到端測試 |

DPI 相關的測試，要在 100%、150% 和多螢幕混合縮放的環境下各跑一次。M0 會先確認 GitHub Actions 的 Windows 環境能不能跑這些測試；不能的話，改成本機一個指令就能執行的腳本。

### 5.5 模型品質回歸

- **合成測試集（公開，放在倉庫中）**：用開源字型，在不同背景上產生日文、英文、韓文的橫排和直排文字圖片。正確答案是已知的，CI 每次都跑。
- **私有測試集（只放在本機）**：你收集的真實截圖。因為有版權，不能放進公開倉庫。改到 OCR 相關程式碼時在本機跑。
- **判定標準**：記錄每種情境的字元錯誤率作為基準線。新的結果比基準線差超過 1 個百分點就判定失敗；確實變好時才更新基準線。
- **C++ 和官方版的一致性**（M0-14 建立）：`tools/eval/check_ocr_equivalence.py` 用 PaddleOCR 官方實作（Python）當參考答案，檢查 C++ 在 CPU 和 DirectML 上的結果：文字完全相同、文字框誤差不超過 2px，並逐字比對字元表。改到 `src/ocr/` 時都要跑一次。這樣「準確度」只需要在 Python 評測，C++ 只要證明和 Python 一致。

### 5.6 翻譯引擎契約測試

- 每個引擎各錄製一組真實的 HTTP 回應（去除金鑰），存成測試資料，CI 離線重播，驗證解析和對齊都正確。
- 另外錄製異常回應：HTTP 429、500、逾時、格式改變，確認都會觸發備援。
- **每天自動檢查**：用一句固定的句子實際呼叫非官方端點。失敗時只發出通知、不擋住合併，目的是在使用者回報之前就知道端點壞了。

### 5.7 效能與資源

- **效能量測工具**：用測試集跑完整流程，記錄每個步驟耗時的中位數和第 95 百分位數，對照 design.md 第 5 節的預算。比上一個版本慢超過 20% 就要查原因。
- **耐久測試**：讓測試目標每隔幾秒換一次內容，連續跑 1～2 小時，並記錄記憶體用量、控制代碼數、GDI 物件數和顯示卡記憶體。任何一項持續成長就代表有洩漏。
- **D3D 除錯層**：除錯版開啟 D3D 除錯層，程式結束時列出沒有釋放的 D3D 物件，數量必須為 0。
- **閒置 CPU**：透鏡開著但畫面沒有變化時，CPU 使用率要低於 1%。

### 5.8 執行期的自我檢查與除錯工具

這些工具的目的是：bug 在使用者的電腦上發生時，也能取得足夠的資訊來重現。

- **斷言**：除錯版中斷言失敗會立即中斷；正式版只記錄，不讓程式當掉。
- **記錄**：每筆記錄都帶透鏡編號和流水號，可以串起同一次處理的完整過程。預設不記錄擷取到的文字、譯文和金鑰。
- **除錯覆蓋框**：在畫面上顯示 OCR 框、狀態機的狀態和各步驟的耗時。
- **除錯傾印**：按快捷鍵，把當下的擷取畫面、OCR 結果、翻譯結果和設定（已移除金鑰）存成一個資料夾。使用者回報 bug 時附上這個資料夾，就能在開發環境重現。
- **當機傾印**：發生未處理的例外時寫出 minidump，可以直接看到當機時的呼叫堆疊。

### 5.9 手動測試矩陣

每個里程碑結束時執行，由你在真實環境中測試：

| 類別 | 測試項目 |
|---|---|
| 顯示 | 縮放比例 100%、125%、150%、175%；兩個螢幕使用不同的縮放比例；HDR 開啟和關閉；高更新率螢幕 |
| 內容 | Chrome、Edge、Firefox 的網頁；本機的漫畫閱讀器；網頁漫畫；韓文條漫；2～3 款使用無邊框視窗模式的遊戲 |
| 操作 | 拖動、縮放、快速來回移動；把透鏡拖到結果視窗上；在透鏡中間點擊和捲動；拖動到另一個螢幕 |
| 環境 | 睡眠後恢復；拔掉或接上螢幕；斷網；用 CPU 模式執行（模擬沒有顯示卡的電腦） |
| 介面（MT-UI） | 結果視窗的捲動、回到最新、置頂、字級、深淺色，以及重新啟動後位置是否還原 |

### 5.10 CI 流程

**每個 PR：**
1. 建置 Debug 和 Release。
2. 檢查 clang-format 格式。
3. 執行 MSVC 靜態分析。
4. 執行單元測試。
5. 開啟 AddressSanitizer，再執行一次單元測試。
6. 執行翻譯引擎契約測試。
7. 執行合成測試集的 OCR 回歸評測（從 M2 開始）。

**每天：** 檢查非官方端點是否還能用（不擋住合併）。

### 5.11 完成的定義

一個任務要同時符合以下條件才算完成：

- [ ] 程式碼完成，沒有新增任何警告
- [ ] core 的新邏輯都有單元測試
- [ ] CI 全部通過
- [ ] 手動驗證的步驟和結果寫在 PR 說明中
- [ ] 經過程式碼審查（使用 Claude Code 的 `/code-review`）
- [ ] 如果設計有改變，已經更新 design.md

### 5.12 發現 bug 時的處理流程

1. **重現**：用除錯傾印或當機傾印，在開發環境重現問題。
2. **先寫一個會失敗的測試**：依照 bug 的類型，寫成單元測試、整合測試，或加進 OCR 測試集。
3. **修正**，確認這個測試通過，其他測試也沒有壞掉。
4. **保留這個測試**，防止同樣的 bug 再次出現。
5. 在 PR 中寫下**根本原因**，而不只是「修好了」。
